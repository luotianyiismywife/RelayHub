## J. 计费与用量维度（2026-08-22 全网调研新增）⭐ 重大遗漏

> ⚠️ **当前阶段不做计费**（2026-08-25 用户拍板）：RelayHub 只转发，计价由上游/中转站自己算，
> 本组全部是**未来规划**（Kernel-billing 计费插件），v1 自用阶段不实现；
> 契约已落的 J1/J2/J11 上游插件侧（TokenUsage + extract_usage）保留（透传 usage 无成本）。
>
> 调研 OpenRouter / LiteLLM / Helicone / Langfuse / New API / one-api / Higress 的价格体系后，发现当前设计（Balance/Usage 窗口/峰谷）**只覆盖了很小一部分**。
> 真正的成本计算是**多维度**的：不同 token 类型费率不同、缓存/推理/图片/音频/视频单独计价、长上下文分档、时间窗条件倍率、流式预扣结算。
> 这些几乎全是 `Kernel-billing` 的职责（上游插件只返回平台数据，不做成本计算）。

| # | 待办 | 说明 | 参考实现 | 状态 |
|---|---|---|---|---|
| J1 | **Token 多维度分类计费** ⭐最大遗漏 | 输入/输出/缓存读/缓存写(5m+1h)/推理/图片输入/图片输出/音频输入/音频输出/视频/工具调用 —— **每维独立费率**，成本 = Σ(各维 token × 各维单价)；契约见 [插件模板分类 §0.6](./02-插件体系/插件模板分类.md)（TokenUsage/PriceTable） | **new-api `TokenParams` 10 维**（P/C/Len/CR/CC/CC1h/Img/ImgO/AI/AO）、OpenRouter 15 维、LiteLLM | ⬜ 契约✅ 已落 |
| J2 | **缓存定价（prompt caching）** | cache read（命中读，约 1/10 价）vs cache write（写入创建，约 1.25x）；**Claude 5min/1h TTL 两种 cache write**；流式响应提取 cached_tokens —— **convert_response 归一化已入模板**（extract_usage） | OpenRouter/LiteLLM/Helicone、Higress ai-statistics（`cached_tokens`） | ⬜ 契约✅ 已落 |

| J4 | **条件倍率规则（峰谷泛化）** | 峰谷 PeakRate 泛化成**条件规则**：时间窗（utc_start/end）+ 请求头/星期/小时/月条件 → 倍率；当前仅 PeakRate（时段）不够 | OpenRouter `PricingOverride`、new-api billingexpr（header/hour/weekday 条件） | ⬜ |

| J6 | **特殊单位计费** | 不是所有模型按 token：realtime 音频按**秒**、图片生成按**张**、视频按秒、web search 按请求 | LiteLLM `audio second`/`output_cost_per_image`、new-api realtime 按秒 | ⬜ |
| J7 | **统一价格表** | 模型多维价格 JSON（litellm 那套），Kernel-billing 消费；自用可裁剪子集 | litellm `model_prices_and_context_window.json` | ⬜ |

| J9 | **缺失值语义** | unknown vs explicit 0 必须区分（不能把未知伪装成免费）；`-1` sentinel 不可当费率 | all-api-hub 调研结论 | ⬜ |

## M. 内核架构规划（2026-08-24）⭐ 写内核的蓝图

> 基于 L 组缺失点分析，给出的内核分层 + 管道 + 状态 + 配置规划。
> 用户 2026-08-24："顺便帮我规划一下内核架构"。

### M.1 七层分层架构

```
入口层    HTTP Server（监听/TLS/路由匹配）+ 协议解析（四协议入口 + trace ID）
  ↓
管道层-去程  on_auth → on_ratelimit（Kernel-* 插件挂载，有序执行）
  ↓
调度层    ModelResolver（模型名→上游）+ 路由策略（权重/健康/轮询）
          + 凭据轮换（sticky/rotation/single）+ 协议选择（capabilities+fallback）
  ↓
转发层    on_pre_forward（billing预扣/audit）→ 头注入+body合并（模板引擎）
          → convert_request（插件出口转换）→ HTTP转发（代理池/SSE管道）
  ↓
响应层    convert_response（插件+extract_usage）→ 出口转换（标准→客户端格式）
  ↓
管道层-回程  on_post_forward（billing结算/usage/logging）→ on_error（retry/alert）
  ↓
基础设施层  配置管理 + 凭据管理 + 插件管理器 + 状态存储 + 代理池管理
```

### M.2 管道钩子清单（L3.1 的答案，B1 落地）

| 钩子点 | 时机 | 可插 | 示例 |
|---|---|---|---|
| `on_request_receive` | 请求进入，协议解析后 | ✅ | 生成 trace ID |
| `on_auth` | 鉴权 | ✅ | Kernel-auth 校验客户端 key |
| `on_ratelimit` | 入站限流 | ✅ | Kernel-ratelimit |
| `on_route` | 选上游 | ❌ 内核 | ModelResolver + 路由策略 |
| `on_pre_forward` | 转发前 | ✅ | Kernel-billing 预扣、Kernel-audit |
| `on_forward` | 转发 | ❌ 内核 | 头注入/body/代理池/SSE |
| `on_response_header` | 收到上游响应头 | ✅ | 状态码判定（http.yaml） |
| `on_response_stream` | 流式分块 | ✅ | Kernel-cache |
| `on_response_complete` | 响应完成 | ✅ | convert_response + extract_usage |
| `on_post_forward` | 转发后 | ✅ | Kernel-billing 结算、Kernel-usage、Kernel-logging |
| `on_error` | 错误 | ✅ | Kernel-retry、Kernel-alert |

### M.3 内核插件 yaml 结构（L3.2 的答案）

Kernel-* 也用 yaml + ts，但挂载点（hooks）不同：

```yaml
# Kernel-billing-1.0.0/kernel.yaml
apiVersion: relayhub.io/v1
kind: Kernel-billing
metadata: { name: billing, version: 1.0.0 }
depends: { kernel: "^0.1" }
hooks:                          # 挂载点 → 函数（与上游插件的 scripts 区分）
  on_pre_forward: { file: ./billing.ts, fn: preConsume }
  on_post_forward: { file: ./billing.ts, fn: postConsume }
config:                         # 插件自身配置（价格表等）
  price_table: ./prices.json    # J7 价格表
  currency: { base: USD, rate: { RMB: 7.3, quota: 500 } }
```

### M.4 状态存储决策（L4.2 的建议）

**SQLite**（单文件、零配置、够用）：
- key 健康标记（rotate 持久化）
- 用量统计（H2 Kernel-usage）
- 日志（H1 Kernel-logging，可选 JSONL）
- 余额缓存（balance_ttl 过期）

**内存**：路由表、模型列表缓存、代理池节点、热数据。

### M.5 config.yaml 完整 schema（L4.1 的建议分段）

```yaml
server:           # 监听/TLS/超时/大小限制

kernel_plugins:   # 内核插件启用
storage:          # SQLite 路径
logging:          # 内核日志（级别/格式/输出）
```
