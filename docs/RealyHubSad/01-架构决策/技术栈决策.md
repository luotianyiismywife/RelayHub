# RelayHub 技术栈决策

> 决策记录（ADR）：语言/运行时选型。
> 用户 2026-08-21 确认：**Rust + TS**（Rust 内核 + TS 插件层）。

---

## 1. 决策

| 层 | 语言 | 职责 |
|---|---|---|
| **内核** | **Rust** | 配置快照、路由/转发、凭据管理、HTTP 服务、插件宿主 |
| **插件层** | **TypeScript** | 上游适配逻辑（转换器、特殊逻辑如 cookie 查询、逆向） |

## 2. 为什么这个组合

| 需求 | Rust | TS |
|---|---|---|
| 内存：内核小 + 每插件 ≤50MB | ✅ 内核本身几 MB~十几 MB | ✅ 运行时吃插件预算 |
| 启动 3 秒 | ✅ 毫秒级启动 | 取决于运行时（见 §3） |
| 声明驱动的灵活适配 | - | ✅ 动态字段、脚本式逻辑，无重编译 |
| 特殊逻辑（cookie 查询/伪装头/逆向） | 写起来痛苦（强类型适配器） | ✅ 天然灵活 |
| 类型安全 | ✅ 编译期 | 可选（TS 本身） |

**本质**：Rust 管"性能和资源"，TS 管"灵活和表达"。微内核用 Rust 守住硬指标，插件用 TS 满足"每个上游都不同"的现实。

### 2.1 内存预算模型（既定：每个插件 50MB）

> 用户 2026-08-21 澄清：**内存预算 = Rust 内核（本身很小）+ 每个插件独立 50MB 预算**。
> 不是"整个 RelayHub 总量 50MB"。

```
总内存 ≈ Rust 内核（几 MB~十几 MB） + Σ 每个加载的插件（各自 ≤50MB）
```

**含义**：

1. 插件运行时选型从"总量紧缩"变为"每插件 50MB" → **deno_core 重新可行**（30-50MB 卡线）
2. 多插件场景：N 个插件 = N×50MB 上限（2 个插件 ≈ 内核 + 100MB）
3. 若插件数量多，需要"按需加载"（不用的插件不载入运行时实例）

## 3. TS 运行时方案（按每插件 50MB 重新评估）

| 方案 | 每插件内存 | 启动 | 单二进制 | TS 支持 | 评价 |
|---|---|---|---|---|---|
| **QuickJS 嵌入**（`rquickjs` crate） | 几 MB | 毫秒级 | ✅ 编译进内核 | 需预编译 TS→JS | ✅ 最省，预算内非常宽松 |
| **deno_core 嵌入** | ~30-50MB | 数百 ms | ✅ | ✅ 原生 TS | ✅ **正好卡进预算线**（50MB 内） |
| **Bun/Node 子进程** | 40-80MB | 1-2 秒 | ❌ 两运行时 | ✅ | ⚠️ 边缘（Node 40MB 勉强，Bun 偏高） |

**新评估**（每插件 50MB 前提下）：

| 维度 | QuickJS | deno_core |
|---|---|---|
| 内存 | 几 MB（宽裕） | 卡线（30-50MB） |
| 原生 TS | ❌ 需预编译 | ✅ 直接跑 TS |
| npm 生态 | 需打包 | ✅ 兼容 |
| 单二进制 | ✅ | ✅ |
| 热重载隔离 | 轻量实例 | 较重 |

> ⚠️ **待定**（2026-08-21 用户暂缓）：两个候选各有取舍：
> - QuickJS：内存最优，但 TS 需预编译、npm 生态要打包适配
> - deno_core：原生 TS + npm 生态，内存正好卡 50MB 预算线
> 建议做一次小规模 spike（原型验证）再定：跑一个真实转换器脚本，量两种方案的内存/启动。

> ⚠️ **待定**（2026-08-21 用户暂缓）：QuickJS 嵌入是最优候选，但需验证：
> - TS 插件生态（npm 包能否打进插件包）
> - 热重载时 QuickJS 实例的隔离/回收
> - 转换器脚本的性能（相对 Rust 原生）

## 4. 插件包形态（既定：yaml + ts 列表）

> 用户 2026-08-21 确认：**插件 = yaml + ts**。
> **yaml 里写的是"实现了哪些功能"**：哪些读 yaml 可以直接组装（静态规则），哪些要调用 ts。
> **ts 实现的不仅是"前端所展示的东西"，还有各平台不一样的逻辑**：比如模型列表——
> 不同平台返回的字段不一定一样，也不一定是 curl 某个接口，这种就需要 ts 了。

```yaml
# openai-1.0.0/（目录式，Cargo/SemVer 版本）
# 文件拆分（推荐按职责，见插件开发规范 §2）：
#   upstream.yaml  功能清单：静态规则（可直接组装）+ scripts 映射（需调用 ts）
#   convert.ts     convert_request / convert_response（协议修正 + usage 归一化）
#   models.ts      list_models（模型列表归一化）
#   quota.ts       quota_balance / quota_usage（计费查询）
#   http.yaml      状态码 → 动作映射（轮换/冷却/重试/透传）
#   package.json   依赖
```

- **yaml**：**声明"实现了哪些功能"**，分两类：
  - **读 yaml 可直接组装**：端点路径/方法、鉴权方式、静态头、字段结构 —— 内核按 yaml 直接组装
  - **声明调用 ts**：`scripts.<钩子名>: <文件路径>`（新格式，2026-08-22 起）列出哪些功能由 ts 实现 —— 内核遇到这些就调 ts
- **ts（按职责拆文件）**：**实现"yaml 组装不了"的功能**：
  - 模型列表（`models.ts`）：不同平台返回字段不一样、不一定是 curl 某个接口（可能是页面/特殊协议）
  - 协议修正（`convert.ts`）：平台怪癖的条件逻辑
  - 余额/用量（`quota.ts`）：各上游接口、返回结构千差万别
  - 逆向/特殊逻辑：cookie 解析、伪装、SSE 改写
- **判断标准**：能 yaml 组装的 → yaml；要逻辑/要请求/要解析的 → ts

## 5. 与上游声明化设计的关系

- 上游声明（yaml）= "规则"（声明层）
- TS 脚本 = "钩子"（convert / models / quota / 特殊逻辑）
- 划分：**能声明的进 yaml，要逻辑的进 TS 脚本**（对应"通用化进 yaml，个性化进 ts"）
