# RelayHub 插件架构设计决策

> 决策记录（ADR）：插件形态选型。
> 背景：研究 CPA（CLI Proxy API）部署形态时发现教程采用"独立 docker 容器"（CPA 单独部署，new-api 通过渠道配置对接）。
> 结论：**RelayHub 采用进程内插件（架构层）+ Docker 容器部署（部署层）**，即"单容器内多插件"；不采用"每适配器一个独立容器"的模式。

---

## 0. 重要澄清：插件化（架构层）与容器化（部署层）正交

> **前提：RelayHub 肯定要容器化（用户 2026-08-21 确认）。**

| 维度 | 选择 | 说明 |
|---|---|---|
| **架构形态** | 进程内插件 | 适配器编译进主程序，config.yaml 启用，不用的不加载 |
| **部署形态** | Docker 容器 | 一个镜像装全部内置插件，挂载 config.yaml + 数据目录 |

两者**不冲突**：镜像里编译进全部内置插件，跑起来就是"单容器 + 进程内插件"。

**因此本决策讨论的"不采用独立容器"，仅指"每个适配器一个独立容器"（CPA 教程那种多容器编排），
而非否定 RelayHub 本身容器化部署。**

---

## 1. 决策背景

LINUX DO 教程中 CPA 的部署方式：

```
NEW API (docker) ──渠道配置──► CPA (docker) ──► ChatGPT 官网
```

CPA 是独立 docker 容器，new-api 通过"渠道"（ChannelTypeCodex=57）对接它。

**用户判断**：对 RelayHub 而言，插件模式比"每适配器一个独立容器"更合适。✅ 同意。

## 2. 方案对比：多容器编排 vs 单容器多插件

| 维度 | 每适配器一个独立容器（CPA 方式） | 单容器多插件（RelayHub 主张） |
|---|---|---|
| 部署 | 多容器 + 端口 + 网络配置 | 单容器，挂载 config.yaml + 数据目录 |
| 内存 | 每个容器 +30~50MB | 进程内共享，<50MB 目标可达 |
| 启动 | 编排依赖，链式启动 | 单容器 3 秒内就绪 |
| 鉴权/凭据 | 跨容器传递，容易泄漏 | 进程内直连，凭据不外泄 |
| 语言 | 需要独立技术栈 | Rust 内核 + TS 插件（微内核哲学，见技术栈决策） |
| 升级 | 每容器单独升级，需滚动编排保证联通 | 换镜像 + 自写滚动策略，秒级完成 |

**本质**：独立容器是"多语言生态"的解法，但 RelayHub 是单语言自用工具（Rust 内核 + TS 插件），没有多语言需求，就没有容器化理由。

## 3. 升级运维：为什么插件比容器好规划（关键决策依据）

### 3.1 容器升级的痛点：保证联通需要滚动机制

docker-compose 的 `docker compose up -d` 升级是 **stop-then-start**：先停旧容器再起新容器，中间有断流窗口。

要"升级不中断"（保证联通），需要滚动机制，典型实现是 K8s：

| 机制 | 解决的问题 |
|---|---|
| RollingUpdate 滚动更新 | 逐个替换旧实例，而非全停全起 |
| readinessProbe 就绪探针 | 新实例就绪前不接流量 |
| preStop / 优雅停机 | 排空在途请求再关闭 |
| Service / 服务发现 | 新实例自动注册，旧实例自动摘除 |
| 副本数 ≥ 2 | 滚动时始终有可用实例 |

这套机制是 K8s 存在的核心理由。但**不是唯一解** —— 见 3.5 反方论证：单 docker 自写滚动策略也可行。

### 3.2 插件升级的本质优势

进程内插件（编译进二进制）：

- **升级 = 换一个二进制 + 重启进程**，进程是原子升级单元
- 重启毫秒~秒级，在 RelayHub 3 秒启动目标之内
- 没有多服务之间的联通协调问题 —— 单进程内部天然一致
- 回滚同样简单：换回旧二进制

不需要：滚动更新、就绪探针、服务发现、流量排空、副本管理。

### 3.3 进程外插件（预留）的升级

即使将来做 gRPC 进程外插件：

- 升级 = 替换插件文件 + 重启该插件进程（RelayHub 管理生命周期）
- 最多加一个"插件健康检查失败自动重启"，比容器编排简单一个数量级
- 仍然不需要 K8s 那套东西

### 3.4 结论

> 插件模式的升级优势是结构性的：**进程是原子的、状态是共享的、联通是内建的**。
> 容器化后依然成立：单容器内多插件共享一个进程，升级单元是镜像。

### 3.5 正式决策：容器化部署 + 自写金丝雀滚动升级（2026-08-21）

**前提确认**：RelayHub 肯定要容器化部署（用户确认）。

**升级策略**：单 docker 部署，**自写金丝雀/滚动升级策略**，不上 K8s：

```
拉新镜像 ─► 金丝雀验证（小流量试跑）─► 切流量到新实例 ─► 健康判定 ─► 成功/回滚
```

**为什么自写而不是上 K8s**：

- 比 K8s 方便且节约资源（不需要 etcd / kubelet / CNI 整套）
- 可自定义滚动方式（滚动节奏、健康判定、回滚条件、金丝雀比例都自己定）
- 2c2g 小 VPS 上 K8s 是奢望，自写脚本足够

**自写滚动要承担的成本（需自己实现）**：

| 要素 | 自写滚动的做法 |
|---|---|
| 副本数 ≥ 2 | 单机跑两份（内存/CPU 翻倍），或先起新容器再切流量 |
| 流量切换 | 反代/Nginx 把流量切到新容器（RelayHub 后面挂 Nginx） |
| 健康检查 | 就绪判定：HTTP 探活 `/healthz` |
| 在途请求排空 | 优雅停机窗口 + 超时处理 |
| 失败回滚 | 新实例异常时切回旧容器 |
| 状态一致性 | 单容器单进程无此问题；多副本时才需考虑 |

**对 RelayHub 的要求**（写进内核设计）：

1. 必须提供 `/healthz` 就绪探针端点
2. 支持优雅停机（SIGTERM 排空在途请求）
3. 状态尽量无状态化（路由表可从 config.yaml 重建），为将来多副本留路

**边界情况**（自写策略要覆盖）：

- 滚动中途失败（新旧容器并存时的流量一致性）
- 新旧版本协议不兼容（回滚到旧版的处理）
- 金丝雀验证不通过（自动回滚判定）

## 4. "插件"的三种形态（选型）

| 形态 | 代表 | 评价 |
|---|---|---|
| 编译期内置适配器 | one-api / new-api / simple-one-api | ✅ **采用**：零依赖、类型安全、性能最好 |
| Go plugin 动态加载 | - | ❌ 不采用：Go 版本必须一致，踩坑无数，Linux only |
| Wasm 插件 | higress | ❌ 不采用：性能损耗，对自用工具过度设计 |

## 5. 最终架构主张

### 第一层（默认）：内置适配器注册表 + config.yaml 启用

```yaml
plugins:
  upstream:            # 上游适配器（内置实现）
    - type: openai     # 启用内置 openai 适配器
    - type: codex      # 启用内置 codex 适配器（CPA 协议）
      credentials: file:./creds/codex.json   # 认证文件
```

- 适配器写进主程序，注册表按 `type` 分发
- config.yaml 声明启用哪些，不用的不加载
- 参考：one-api 的 `adaptor` 接口 + simple-one-api 的配置即路由

### 部署形态：单容器多插件（Docker 镜像）

```
relayhub:latest ──► /relayhub [主进程 + 全部内置插件]
                     ├── /config/config.yaml   （挂载卷）
                     ├── /data/                （挂载卷：日志/凭据/缓存）
                     └── :8080  /healthz        （HTTP API + 就绪探针）
```

- 一个镜像 = 一个二进制 + 全部内置插件
- 升级 = 换镜像 + 自写金丝雀滚动（见 3.5）
- Nginx 前置反代（同时充当滚动切换的流量入口）

### 第二层（预留）：进程外插件协议

将来要接第三方生态时，定义 **gRPC/HTTP 插件协议**（类似 MCP）：

- 插件是独立进程（任意语言），RelayHub 负责拉起 / 健康检查 / 崩溃重启
- 与"每适配器一个 docker 容器"的区别：**生命周期由 RelayHub 管理**，用户不感知 docker
- 内核只维护一份插件 SDK 的接口定义

### 明确不引入

- ❌ Wasm 沙箱（自用工具不需要为安全付出性能）
- ❌ go plugin 动态加载（版本锁定地狱）
- ❌ K8s 编排（单机自写金丝雀滚动足够，见 3.5）

## 6. 对插件接口设计的要求（来自 CPA 调研）

1. **鉴权可插拔**：普通 Key / JSON OAuth 认证文件 / 订阅号池，接口要支持结构化的凭据类型（`credentials` 可以是文件路径、环境变量、内联 JSON）
2. **凭据生命周期**：认证文件需要自动刷新（new-api 每 10 分钟检查）→ 适配器接口要有 `RefreshCredentials()` 扩展点
3. **协议三件套**（写网页转 API 插件时的范本）：
   - 协议适配：请求路径 + 请求/响应体转换
   - 特殊鉴权：定制请求头（`chatgpt-account-id`、`originator` 等）
   - 凭据自动刷新：定时任务 + 过期前刷新

## 7. 参考源码

- new-api `relay/channel/codex/`：进程内适配器范本（接口 + OAuth Key + 刷新）
- simple-one-api：config 即路由，无 DB 轻量范式
- higress：wasm 插件（反面教材，证明过度设计）
