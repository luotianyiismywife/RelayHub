# 凭据轮换与错误处理约定

> 设计文档：上游插件的"API Key 自动轮换"错误判定契约 + 钩子错误处理约定。
> 调研基础：tokenrhythm-copilot 多 API Key 轮换系统（已实施，含完整状态机与测试矩阵）。
> 核心：**错误判定（什么错误能换 key）在插件，轮换机制（怎么换）在内核**。
> 2026-08-21 用户修正：**single/sticky 模式、并发控制、冷却都是内核的事**，插件只声明判定 + 余额有效期。

---

## 1. 为什么需要

多账号/多 key 场景，单个 key 失效（余额不足/无效/限流）需要**自动切换到下一个**。
但"什么错误算失效"**每个平台不一样**：

| 平台 | 余额不足 | key 无效 | 限流 | 服务端繁忙 |
|---|---|---|---|---|
| tokenrhythm | 402 + INSUFFICIENT_BALANCE + "余额不足" | 401 | 429 | 503 |
| 其他平台 | 可能 400 + 别的文本 | 401 | 429 | 500/502/503 |

**结论**：错误判定不能写死在内核，要由插件声明（对应待办 A3）。

## 2. 插件声明 —— 只含判定

**两处声明**（判定在插件）：

```yaml
# upstream.yaml（插件：只声明判定 + 错误文本模式）
rotation:
  http_rules: ./http.yaml        # ✅ 状态码 → 动作映射（完整表见下）
  error_patterns:              # ✅ 能换 key 的错误文本（不区分大小写）
    - "余额不足"
    - "insufficient_balance"
    - "INSUFFICIENT_BALANCE"
    - "RATE_LIMITED"
    - "UPSTREAM_RATE_LIMITED"
  balance_ttl: 5m              # ✅ 余额有效期（平台相关：余额会变/查询成本高）
                               #   过期后内核重新查询，TTL 内用缓存
  # ❌ 没有 mode / cooldown / transient —— 那是内核的机制（见 §3）
```

```yaml
# http.yaml —— 完整状态码 → 动作映射（2026-08-22 新增，YAML 原生支持注释）
# 覆盖所有状态码怎么处理；模板与 3 示例已带各自实测版本
# 📄 完整字段说明在文件头注释（Template/UpStream/Api/example-plugin/http.yaml）
version: 1
default:
  action: passthrough
  rotatable: false
  retryable: false
codes:
  "400": { action: passthrough, reason: bad_request }
  "401": { action: rotate, reason: invalid_credential, rotatable: true, retryable: true }
  "402": { action: rotate, reason: insufficient_balance, rotatable: true, retryable: true }
  "403": { action: passthrough, reason: forbidden }
  "404": { action: passthrough, reason: not_found }
  "408": { action: retry, reason: request_timeout, retryable: true }
  "409": { action: passthrough, reason: conflict }
  "413": { action: passthrough, reason: payload_too_large }
  "415": { action: passthrough, reason: unsupported_media_type }
  "422": { action: passthrough, reason: unprocessable_content }
  "429": { action: cooldown, reason: rate_limited, rotatable: true, retryable: true }
  "500": { action: retry, reason: internal_server_error, retryable: true }
  "501": { action: passthrough, reason: not_implemented }
  "502": { action: retry, reason: bad_gateway, retryable: true }
  "503": { action: retry, reason: service_unavailable, retryable: true }
  "504": { action: retry, reason: gateway_timeout, retryable: true }
```

**http.yaml 字段级说明**（精简；完整版见模板 http.yaml 文件头注释）：

| 字段 | 含义 |
|---|---|
| `version` | 文件格式版本（当前 = 1） |
| `default` | 兜底规则：状态码未列出时的处理（安全默认 = passthrough） |
| `codes` | 状态码 → 规则 映射（key = 字符串化状态码） |
| 规则.`action` | `rotate` / `cooldown` / `retry` / `passthrough` |
| 规则.`reason` | 人类可读原因（日志/告警展示） |
| 规则.`rotatable` | 该状态码是否参与换 key（省略 = false） |
| 规则.`retryable` | 该状态码是否参与重试（省略 = false） |

**动作语义**（判定在插件，机制在内核）：

| action | 含义 | 内核怎么做 | 典型状态码 |
|---|---|---|---|
| `rotate` | 确定性凭据失效 | 持久化标记 key 不可用，换下一个 | 401（无效）/ 402（余额不足） |
| `cooldown` | 瞬态限流 | 内存冷却该 key（时长 config.yaml），换下一个 | 429 |
| `retry` | 服务端/超时 | 指数退避重试（次数 config.yaml），可换 key | 500/502/503/504/408 |
| `passthrough` | 客户端错误 | 直接返回客户端，不重试不轮换 | 400/403/404/422 等 4xx |
| `default` | 未列出状态码 | passthrough（安全兜底） | — |

- `rotatable` / `retryable`：显式标记是否参与轮换/重试（省略 = false）
- 错误**文本**模式（body error code）→ `rotation.error_patterns`（上）
- 机制（冷却时长/重试次数/换 key 模式）全在**内核 config.yaml**，不在 http.yaml

**默认值**（tokenrhythm 实测，`http.yaml` 内）：401/402 → rotate，429 → cooldown，5xx → retry。

### 2.1 余额有效期（balance_ttl）

> 用户提出：**上游插件和内核要能识别有有效期的余额**。

- 余额不是恒定值（会被消耗/充值），也不是每次请求都能廉价查询
- `balance_ttl` 平台相关：tokenrhythm 有 cookie 查询成本 → 5m；其他平台可能 30s 或 1h
- 内核行为：TTL 内用缓存余额（用于预检/路由），过期重新查询
- 与 `quota_balance` 钩子配合：钩子查原始数据，内核按 TTL 缓存

## 3. 内核轮换机制（通用，不平台相关）

```
请求 → 用 key A 转发
  ├─ 成功 → 结束
  └─ 失败 → 按 http.yaml 查该状态码的动作（判定在插件）
        ├─ passthrough（400/403/404/422 等客户端错误）→ 直接返回客户端，不重试不轮换
        └─ rotate（401/402 确定性失效）→ 持久化标记不可用，换 key B 重试
        └─ cooldown（429 瞬态限流）→ 内存冷却（时长 config.yaml），换 key B 重试
        └─ retry（5xx/408/504 服务端/超时）→ 指数退避重试（次数 config.yaml），可换 key
              └─ 全部 key 试完仍失败 → 返回最后一个错误 + 记日志
```

**关键区分**（tokenrhythm 已验证，与 http.yaml 动作对应）：
- **确定性失效**（401/402 → rotate）：持久化标记，换 key 有效
- **瞬态限流**（429 → cooldown）：冷却后恢复，换 key 可能有效
- **服务端/超时**（5xx/408/504 → retry）：指数退避重试，换 key 无意义但无害
- **客户端错误**（400/403/404/422 → passthrough）：换 key 没用，直接返回

> ⚠️ 与 http.yaml 的关系：**判定数据在插件（http.yaml 的 action），内核只执行机制**（§3）。
> 动作与状态码的映射以 http.yaml 为准，本节是内核的执行逻辑描述。

### 3.1 多用户并发控制（内核职责，用户提出）

> single/sticky 模式在多用户并发下会复杂化，这是**内核要解决的**：

| 并发问题 | 内核处理 |
|---|---|
| 多个并发请求钉同一 sticky key | 游标 + 引用计数：key 被占时排队/换下一个 |
| key 失效时并发中的切换 | **原子切换**（锁），避免重复切换 |
| 余额预检并发一致性 | 余额缓存 + TTL，预检不并发重复查 |
| 同一 key 并发超额使用 | 计数/配额，或依赖平台限流兜底 |

- 插件**不感知并发**：它只声明判定，内核保证并发安全
- 并发粒度：RelayHub 单进程内并发（自用工具），多实例并发待定

## 4. 钩子错误处理约定（A3 待办，一并定）

| 钩子 | 抛错时内核行为 |
|---|---|
| `convert_request` / `convert_response` | **失败 → 中断请求**（协议转换错，重试无意义）→ 转错误响应 |
| `list_models` | 失败 → **保留旧列表**（静默降级，记日志） |
| `quota_balance` / `quota_usage` | 失败 → 显示"不可用"或旧缓存 |
| `refresh_credentials` | 失败 → **标记凭据不可用**（转轮换判定），不中断在途请求 |
| `validate_credential` | 失败 → 该凭据本次不用（换下一个） |

**通用原则**：
- 数据类钩子失败（list_models/quota_*）：**静默降级**，不阻塞主流程
- 转换类钩子失败（convert_*）：**中断**，转错误响应
- 凭据类钩子失败（refresh/validate）：**触发轮换判定**（见 §2/§3）

## 5. key 使用模式（内核机制，非插件配置）

> 用户修正：**single/sticky/rotation 模式是内核的事，不进插件 yaml**（涉及多用户并发）。
> 用户通过 config.yaml 配置（不是插件）。

| 模式 | 行为 | 适用 |
|---|---|---|
| `sticky`（默认） | 固定一个 key，失效才切换 | 前缀缓存命中率最高 |
| `rotation` | 每次请求轮换 | 均摊用量 |
| `single` | 只用指定 key | 单 key 场景 |

```yaml
# config.yaml（内核配置，非插件）
rotation_engine:
  mode: sticky        # sticky | rotation | single
  cooldown: 10m       # 瞬态冷却时长
```

## 6. 对内核的要求

1. 通用轮换引擎：按 http.yaml 查状态码动作（rotate/cooldown/retry/passthrough）→ 标记/冷却/重试 → 换 key
2. 判定数据来自插件（§2：http.yaml + error_patterns + balance_ttl），内核只实现机制（§3）
3. 全部 key 试完仍失败 → 报错（列出脱敏 key + 原因）
4. 自愈：请求成功 → 恢复 key 可用
5. 多用户并发控制（§3.1）：游标/引用计数/原子切换/余额缓存
6. 余额有效期（§2.1）：TTL 缓存，过期重新查询
7. 与协议轮换（平台差异 SAD §3.4）叠加：先切协议，再切 key
