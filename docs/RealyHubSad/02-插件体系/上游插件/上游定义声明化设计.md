# 上游定义声明化设计（YAML 描述上游）

> 设计决策：RelayHub 的上游插件采用 **YAML 声明**（declarative），而非代码插件（imperative）。
> 用户 2026-08-21 提出：上游插件可以写成 yaml，把配置信息、认证信息、支持的 API 类型、
> 每个类型的接口、特殊信息都写进去。
> 内核只需一个"通用转发引擎"，由 yaml 驱动。

---

## 1. 核心思想

**上游适配器从"代码"降维成"配置"**：

```
传统（one-api / new-api）：每个上游写一个 Go 适配器（adaptor 接口）
RelayHub：每个上游写一个 YAML 文件，内核跑通用转发引擎
```

```
┌─────────────────────────────────────────────────────┐
│ RelayHub 内核                                        │
│                                                     │
│  ┌──────────────┐    ┌──────────────────────────┐   │
│  │ 插件管理器    │    │ 通用转发引擎（generic relay）│   │
│  │              │    │  ├─ 端点分发（按 yaml apis）│   │
│  │ · 加载/校验  │    │  ├─ 鉴权（向插件管理器取凭据）│   │
│  │  上游 yaml   │    │  ├─ 请求头（yaml + 凭据注入）│   │
│  │ · 管理凭据   │    │  ├─ 格式匹配（查 capabilities）│   │
│  │  （引用/刷新）│    │  └─ 参数修正（scripts 钩子）  │   │
│  │ · 凭据注入   │───►│      （不做格式转换，不匹配报错）│   │
│  └──────────────┘    └──────────────────────────┘   │
│                                                     │
│  config.yaml ──► 插件管理器 ──► 加载上游定义 yaml     │
└─────────────────────────────────────────────────────┘
```

## 2. 三层职责分离（核心设计）

> 用户 2026-08-21 澄清：**yaml 只写通用信息（规则），凭据文件引用由插件管理器管理，
> 转发引擎执行。yaml 只是告诉转发引擎"上游的规则"。**

| 层 | 职责 | 内容 | 是否含敏感信息 |
|---|---|---|---|
| **YAML 上游定义** | 声明协议规则 | 端点路径/方法、鉴权类型、头映射模板、转换器引用 | ❌ 不含凭据值 |
| **插件管理器** | 托管凭据 | 凭据文件引用、加载、刷新、按需注入 | ✅ 持凭据（文件/内存） |
| **转发引擎** | 执行转发 | 端点分发、向插件管理器取凭据、注入请求头、转换、转发 | 不持有，只使用 |

**信息流**：

```
YAML（规则）──► 插件管理器（解析规则 + 关联凭据引用）──► 转发引擎（按规则 + 凭据执行）
       只声明"怎么连"        持有"用什么连"                 实际"去连"
```

**关键点**：

1. YAML 里的 `credentials` 只是**引用**（如 `credentials: ref:codex-prod`），不是凭据本身
2. 凭据本体（认证文件、key 内容）只存在于插件管理器管理的位置（文件系统/环境变量/secret 文件）
3. 转发引擎不感知凭据来源，只从插件管理器拿"注入后的请求头集合"
4. 好处：
   - yaml 可公开、可提交仓库（不含密钥）
   - 凭据文件独立管理（权限 600、不入库、可轮换）
   - 同一份 yaml 可配多套凭据（多账号轮换/多环境）

---

## 3. 威力

| 收益 | 说明 |
|---|---|
| 新增上游不用编译 | 写个 yaml 文件，config.yaml 引用即可 |
| 升级上游不用换二进制 | 改 yaml = 改协议，可热重载 |
| 内核只有一套转发引擎 | 所有上游共用一个通用中继，yaml 只是参数 |
| 与 config.yaml 一把梭统一 | 上游也是配置，不是代码 |
| **凭据与规则分离** | yaml 可入库公开，凭据文件独立托管（600 权限/可轮换） |

## 4. 插件分工：yaml + ts 列表（既定决策 2026-08-21）

> 用户确认：**插件 = yaml + ts**。
> - **yaml** 实现可通用化的东西（如 openai 三个端点是什么、鉴权方式、字段结构）
> - **ts** 实现每个上游不一样的点（如余额查询、用量查询）
>
> 进一步明确：**内核直接调用脚本查询信息**；**内核和脚本共同定义一套标准字段格式/标准接口**
> （如"查询余额"用哪个、"查询模型列表"用哪个）。所以其实是 **yaml + ts 列表**。

### 4.1 分工原则

| 层 | 管什么 | 举例 |
|---|---|---|
| **yaml（声明）** | 可通用化的静态规则 | 端点路径/方法、鉴权类型、字段结构、静态头、脚本列表索引 |
| **ts（脚本列表）** | 每个上游不一样的标准接口实现 | 余额查询、用量查询、模型列表、cookie 解析、特殊计费 |

**判断标准**：

- 多个上游**长得一样**的部分 → 进 yaml（通用化）
- 这个上游**独有**的逻辑 → 进 ts（个性化）

### 4.2 功能清单：哪些 yaml 组装，哪些调 ts（核心决策）

> 用户澄清（两次）：
> 1. ts 实现的不只是前端展示的东西，还有**各平台不一样的逻辑**（如模型列表——不同平台字段不一定一样、不一定是 curl 某个接口）
> 2. **yaml 里写的是"实现了哪些功能"**：哪些读 yaml 可直接组装，哪些直接调用 ts

**核心原则**：

```
能 yaml 组装的 → yaml（静态声明，内核直接按规则组装）
要逻辑/请求/解析的 → ts（动态实现，内核调用脚本）
```

**yaml = 功能清单**，每个功能标注"组装方式"：

| 功能 | 组装方式 | 说明 |
|---|---|---|
| 端点路径/方法 | ✅ yaml 直接组装 | openai 三个端点是什么，写死即可 |
| 鉴权方式/头 | ✅ yaml 直接组装 | bearer/header/静态头 |
| 字段结构 | ✅ yaml 直接组装 | 请求/响应简单映射 |
| **模型列表** | **🔧 调 ts** | 不同平台返回字段不一定一样，也不一定是 curl 某个接口 |
| **余额/用量** | **🔧 调 ts** | 各上游接口、返回结构千差万别 |
| **逆向/特殊逻辑** | **🔧 调 ts** | cookie 解析、伪装、SSE 改写 |

**yaml 示例（功能清单 + 组装规则）**：

```yaml
# <插件名>-<版本>/upstream.yaml（目录式，完整结构见 §9）
apiVersion: relayhub.io/v1
kind: Upstream-api-balance       # 三级 kind（凭据 × 计费）
metadata:
  name: openai
  version: 1.0.0                 # Cargo/SemVer 三级，与目录名一致
depends:
  kernel: "^0.1"

# 这些由 yaml 直接组装（静态规则）
# apis 的 key = 协议名（openai / anthropic / responses / gemini），内核按协议分发
apis:
  openai:            { path: /v1/chat/completions, method: POST }
  anthropic:         { path: /v1/messages, method: POST }
  responses:         { path: /v1/responses, method: POST }
  gemini:            { path: /v1beta/models/*:generateContent, method: POST }  # 可选
  models:            { path: /v1/models, method: GET }     # 通用端点
  embeddings:        { path: /v1/embeddings, method: POST } # OpenAI 系
auth:
  type: bearer
  key_field: Authorization

# 这些声明"由 ts 实现"（内核调用脚本，不自己组装）
# 钩子 → 文件/函数 显式映射（内核按此加载，不猜目录结构）
scripts:
  list_models:    ./models.ts          # 函数名 = 钩子名（默认）
  quota_balance:  ./quota.ts
  quota_usage:    { file: ./quota.ts, fn: getUsage }   # 或指定函数名

# key 轮换错误判定（平台相关，可选；不声明用默认值）
# http.yaml = 完整状态码 → 动作映射（rotate/cooldown/retry/passthrough）
rotation:
  http_rules: ./http.yaml              # ✅ 状态码 → 动作映射（按平台实测改）
  error_patterns: ["insufficient_balance", "rate_limited"]  # 错误文本模式
  balance_ttl: 5m                      # ✅ 余额有效期（可选）
  # ❌ 没有 mode / cooldown / transient —— 那是内核机制（config.yaml 配）
```

**apis key = 协议名**（内核按协议分发）：

| apis key | 协议 | 说明 |
|---|---|---|
| `openai` | OpenAI 兼容 | `/v1/chat/completions`（兼容一切，90% 平台覆盖） |
| `anthropic` | Anthropic | `/v1/messages`（配 `special.headers.anthropic`） |
| `responses` | Responses | `/v1/responses` |
| `gemini` | Gemini | `/v1beta/models/*:generateContent`（Google 系，可选） |
| `models` | 通用 | 模型列表 |
| `embeddings` | OpenAI 系 | 嵌入 |

> **内核内置四协议：openai / anthropic / responses / gemini**。
> 其他协议（Ollama、私有格式等）用 ts 实现（`convert_request` 手工处理）。
> 内核看到 `apis.anthropic` 即知：走 Anthropic 协议 → 注入对应强制头 → convert_request(protocol=anthropic)。
> 协议名与 `special.headers.<协议名>`、`convert_request` 的 `ctx.protocol` 三者对齐，无需映射表。

**ts = 实现"yaml 组装不了"的功能**：

```ts
// models.ts —— 每个钩子一个实现，返回内核/展示需要的统一结构
export async function list_models(ctx: Ctx) {
  // 不同平台：可能是 curl 一个接口、解析页面、走特殊协议……
  // 内核不关心怎么拿到的，只消费统一返回结构
  return [{ id: "gpt-4o", name: "GPT-4o", price: 0.005 }]
}

// quota.ts
export async function quota_balance(ctx: Ctx) {
  return { total: 5.2 }          // ← 新契约字段是 total（旧 balance 已废弃）
}
```

**要点**：

1. **yaml 是"功能清单 + 组装规则"**：内核加载时，看到"哪些直接组装"（静态规则）、"哪些调 ts"（scripts 映射）
2. **ts 覆盖"yaml 组装不了"的一切**：模型列表（平台字段不一/非 curl）、余额、用量、逆向
3. **内核直接调用脚本**：读 `scripts` → 找文件 → 找函数 → 调用（不经入口文件中转）
4. **文件组织自由**：简单插件一个文件全放，复杂插件按功能拆文件，yaml 逐个指向
5. **统一返回结构**：ts 内部怎么做都行，但返回给内核的字段格式是契约（展示层/内核按此消费）

### 4.3 插件 = yaml + ts 列表

```
openai-1.0.0/
├── upstream.yaml      # 静态规则 + 钩子→文件映射（scripts）
├── models.ts          # list_models 实现
├── quota.ts           # quota_balance / quota_usage 实现
└── package.json       # 依赖
```

```yaml
# upstream.yaml（示例：yaml 声明规则 + 钩子映射）
name: openai
version: 1.0.0
apis:                          # key = 协议名（内核按协议分发）
  openai:          { path: /v1/chat/completions, method: POST }
  embeddings:      { path: /v1/embeddings, method: POST }
  models:          { path: /v1/models, method: GET }
auth:
  type: bearer
  key_field: Authorization
scripts:
  quota_balance: ./quota.ts      # 钩子 → 文件（函数名 = 钩子名）
  quota_usage:   ./quota.ts
  list_models:   ./models.ts
```

**"yaml + ts 列表"的含义**：

- **yaml 列表**：功能清单 —— 哪些读 yaml 直接组装（apis / auth / special 静态规则），哪些调 ts（scripts 映射）
- **ts 列表**：实现"yaml 组装不了"的功能（模型列表 / 余额 / 用量 / 逆向逻辑），yaml 声明每个钩子调哪个文件哪个函数
- 两者合起来 = 一个完整的插件

### 4.4 边界的例子

| 功能 | 组装方式 | 为什么 |
|---|---|---|
| 端点路径 / 方法（openai 三个端点） | ✅ yaml 直接组装 | 静态规则，写死即可 |
| 鉴权方式 + 静态头 | ✅ yaml 直接组装 | bearer/header/静态头 |
| 简单字段映射 | ✅ yaml 直接组装 | 请求/响应简单映射 |
| **模型列表（`list_models`）** | **🔧 调 ts** | 不同平台返回字段不一定一样，也不一定是 curl 某个接口 |
| **余额（`quota_balance`）、用量（`quota_usage`）** | **🔧 调 ts** | 各上游接口、返回结构千差万别 |
| **usage 多维明细归一化（`convert_response` 内）** | **🔧 调 ts** | 平台返回的 usage 明细字段名各异（缓存读/推理等子维度），归一化成 TokenUsage 供内核计算（见插件模板分类 §0.6 / 待办 J 组） |
| **逆向 / 特殊逻辑** | **🔧 调 ts** | cookie 解析、伪装、SSE 改写 |

## 5. YAML Schema 草案（凭据只写引用）

### 5.1 普通上游（OpenAI 官方）

```yaml
# openai-1.0.0/upstream.yaml（目录式，Cargo/SemVer 版本）
apiVersion: relayhub.io/v1
kind: Upstream-api-balance       # ← 三级 kind（凭据 × 计费）
metadata:
  name: openai                  # ← 与目录名一致
  version: 1.0.0                # ← Cargo/SemVer 三级，与目录名一致
  labels:
    vendor: openai
description: OpenAI 官方 API

depends:
  kernel: "^0.1"                 # Cargo 依赖声明

auth:
  type: bearer                # bearer | header | query | oauth-file | account-pool
  key_field: Authorization
  key_prefix: "Bearer "
  credentials: ref:openai-prod   # ← 只写引用，凭据本体由插件管理器托管

apis:                          # key = 协议名（内核按协议分发）
  openai:
    path: /v1/chat/completions
    method: POST
  embeddings:
    path: /v1/embeddings
    method: POST
  models:
    path: /v1/models
    method: GET
  responses:
    path: /v1/responses
    method: POST

special:
  stream_support: true
  sse_format: openai          # openai | anthropic | custom
```

### 5.1.1 转发凭据 vs 查询凭据（平台相关！）

> 用户 2026-08-22 提出：**有的上游只要 key，有的需要 key + session/cookie 来查余额/套餐余量**。
> 规则每个上游不一样，须写进插件。

| 平台形态 | 转发（API 请求） | 查余额/套餐（quota_balance/usage） |
|---|---|---|
| **只要 key** | key（Bearer） | key 即可（OpenAI 官方、one-api） |
| **key + cookie** | key（Bearer） | **额外 cookie/session**（tokenrhythm：key 转发 + tr_session 查余额） |

```yaml
# 只要 key 的平台（转发 + 查询都用 key）
auth:
  type: bearer
  key_field: Authorization
  credentials: ref:xxx-prod

# key + cookie 查余额的平台（转发用 key，查询用 cookie）
auth:
  type: bearer
  key_field: Authorization
  credentials: ref:xxx-prod          # 转发用 key
  query:                              # 查余额/套餐的附加凭据（可选）
    cookie: ref:xxx-session           # 余额查询专用 cookie/session
```

**要点**：
1. `credentials`（key）= 转发专用，注入所有 API 请求
2. `query.cookie`（可选）= 查余额/套餐专用，只在 `quota_balance` / `quota_usage` 钩子执行时注入
3. 一个 cookie 可绑定多个 key（tokenrhythm 实测：余额按 cookie 粒度查询并缓存）
4. 只有 key 就能查的平台不需要 `query` 段

### 5.2 特殊上游（CPA Codex）

```yaml
# codex-cpa-1.0.0/upstream.yaml（目录式，Cargo/SemVer 版本）
apiVersion: relayhub.io/v1
kind: Upstream-api-balance
metadata:
  name: codex-cpa
  version: 1.0.0

auth:
  type: oauth-file            # JSON 认证文件（CPA 认证文件）
  fields:                     # 认证文件字段 → 请求头映射（模板，不含值）
    Authorization: "Bearer {access_token}"
    chatgpt-account-id: "{account_id}"
  refresh:                    # 凭据自动刷新（由插件管理器执行）
    every: 10m
    expires_within: 24h       # 到期前 24h 刷新（new-api 策略）
  credentials: ref:codex-prod # ← 引用，凭据文件由插件管理器加载/刷新

apis:
  responses:
    path: /backend-api/codex/responses
    method: POST
  responses_compact:
    path: /backend-api/codex/responses/compact
    method: POST
  alpha_search:
    path: /backend-api/codex/alpha/search
    method: POST

special:
  headers:                    # 静态请求头（伪装 CLI，无敏感信息）
    - originator: codex_cli_rs
    - OpenAI-Beta: responses=experimental
    - Content-Type: application/json
  force_content_type: true    # 强制精确媒体类型
```

### 5.3 复杂上游（参数修正钩子，格式匹配架构）

> 2026-08-24 更新：**不做格式转换**，改为**格式匹配+报错**——
> 客户端格式不在 capabilities 里 → 直接 400 报错。
> 插件 `convert_request/response` 只做同格式内的参数修正（平台怪癖）+ usage 归一化。
> 上游支持客户端格式 → 零修正直接转发；有怪癖 → 插件写 ts 钩子。

```yaml
# anthropic-1.0.0/upstream.yaml
apiVersion: relayhub.io/v1
kind: Upstream-api-balance
name: anthropic
version: 1.0.0
auth:
  type: header
  key_field: x-api-key
  credentials: ref:anthropic-prod

apis:                          # key = 协议名（内核按协议分发）
  anthropic:
    path: /v1/messages
    method: POST

scripts:                       # 参数修正（同格式内，有怪癖才写）
  convert_request:  ./convert.ts   # 请求参数修正（anthropic 必带头等，不做格式转换）
  convert_response: ./convert.ts   # 响应修正 + usage 归一化
```

### 5.4 插件管理器的凭据配置（凭据本体在 yaml 之外）

```yaml
# credentials.yaml（仅含引用，值由 docker secret 提供）
credentials:
  openai-prod:
    type: api-key
    secret: openai_api_key            # docker secret 名（/run/secrets/openai_api_key）
  codex-prod:
    type: oauth-file
    secret: codex_auth_file           # 认证文件作为 secret 挂载
  anthropic-prod:
    type: api-key
    secret: anthropic_key
```

> **插件管理器职责**：解析 `ref:` 引用 → 定位凭据源（docker secret）→ 加载进内存 →
> 按需提供给转发引擎 → 管理刷新（oauth-file 定时刷新）。
>
> **转发引擎视角**：不感知凭据来源，只从插件管理器拿到"已注入的请求头集合"。

### 5.5 凭据存储：docker secret（既定决策 2026-08-21）

> 用户确认：凭据文件加密使用 **docker secret** 存储。

**容器内 secret 挂载路径**：

```
/run/secrets/<secret_name>
  ├── openai_api_key      # 内容即 API key（单行文本）
  └── codex_auth_file     # 内容即 JSON 认证文件（oauth-file）
```

**docker-compose 声明示例**：

```yaml
services:
  relayhub:
    image: relayhub:latest
    secrets:
      - openai_api_key
      - codex_auth_file

secrets:
  openai_api_key:
    file: ./secrets/openai_api_key      # 源文件在宿主（权限 600）
  codex_auth_file:
    file: ./secrets/codex_auth_file
```

**为什么用 docker secret 而非明文挂载**：

| 维度 | docker secret | 明文卷挂载 |
|---|---|---|
| 磁盘明文 | 内存 tmpfs（compose 下宿主机文件仍存在，但容器内不落盘） | 容器内直接可见明文 |
| 权限控制 | 仅容器内进程可读（/run/secrets 权限 444） | 取决于挂载权限 |
| 与配置分离 | 凭据 yaml 只写引用，不碰值 | 值直接进 yaml |
| 轮换 | 重建容器即换 secret | 需手动改挂载内容 |
| 通用性 | compose / swarm / k8s 均支持 | 所有环境通用但无保护 |

**对内核的要求**：

1. 凭据解析统一走 `/run/secrets/<name>`（支持自定义路径，如非容器环境）
2. 加载时校验权限（日志提示，不强制 600）
3. 加载后存内存，不写日志、不 dump
4. oauth-file 类凭据刷新后的新值**也写回内存**，不落盘（保持 secret 语义）

### 5.6 请求头声明化（顶层 `headers` 字段）

> 2026-08-24 新增：**请求头全部声明进 yaml**，伪装/定制头不再需要写 ts。
> 场景来源：opencode zen 上游（免费模型 + 伪装 opencode CLI 请求头）。
> 原则："能 yaml 组装的 → yaml" —— 请求头属于静态规则，归 yaml，不归 convert_request。

**为什么不能只用 `special.headers`**：

| 需求 | special.headers 的局限 | headers 字段解决 |
|---|---|---|
| 所有协议统一注入（openai + responses 都要带 UA） | 每个协议各写一遍，重复 | 顶层 `headers` 一次声明全部生效 |
| 动态值（session/request ID 每请求不同） | 只能写死 | 模板占位符 `{{...}}` 由内核解析 |
| 版本漂移（UA 里的版本号会过时） | 写死就冻结 | `{{ref:...}}` 从 config.yaml 读，用户可改 |

**三种取值方式**：

| 语法 | 含义 | 解决什么 |
|---|---|---|
| `"cli"` | 静态字符串，直写 | `x-opencode-client` / `x-opencode-project` 等固定值 |
| `"ses_{{random:8}}"` | 模板占位符，内核每次转发时生成 | session/request ID —— **必须动态**，否则所有请求同一 ID 特征明显 |
| `"{{ref:user_agent}}"` | 从 config.yaml 读取（插件管理器注入） | 版本漂移：UA 版本号会过时，让用户在 config.yaml 改，不动插件 |

**占位符语法（`{{...}}`）**：

| 占位符 | 语义 | 示例结果 |
|---|---|---|
| `{{random:N}}` | 随机 N 位 hex（长度可配） | `{{random:8}}` → `a1b2c3d4` |
| `{{uuid}}` | 完整 UUID | `550e8400-...` |
| `{{var:<名>}}` | 请求级变量：首次生成、同请求复用 | `ses_{{var:rid}}` + `msg_{{var:rid}}` 共享同一随机串 |
| `{{ref:<config路径>}}` | 从 config.yaml 读取 | `{{ref:user_agent}}` |
| `{{client_header:<名>}}` | 透传客户端请求头 | `{{client_header:x-request-id}}` |

> `{{var:<名>}}` 解决真实 CLI 的关联性：opencode 抓包显示 session 和 request 共享同一随机串
> （`x-opencode-session: ses_po1nt9` / `x-opencode-request: msg_po1nt9`）。
> 两个独立 `{{random:8}}` 无法表达这种关联，`{{var:rid}}` 可以在一个请求内复用同一生成值。

**与 special.headers 的分层与优先级**：

```yaml
headers:                  # ① 全局头：所有协议都注入（新增）
  x-opencode-client: "cli"
  ...
special:
  headers:
    openai:               # ② 协议头：仅某协议注入（现有机制，保留）
      User-Agent: "{{ref:user_agent}}"
```

优先级：`special.headers.<协议>` > `headers`（协议级覆盖全局）。合并规则照抄现有 special.headers 语义。

**完整示例（opencode zen 上游）**：

```yaml
apiVersion: relayhub.io/v1
kind: Upstream-api-free
metadata:
  name: opencode-zen
  version: 1.0.0

apis:
  openai:    { path: /v1/chat/completions, method: POST }
  responses: { path: /v1/responses, method: POST }
  models:    { path: /v1/models, method: GET }

auth:
  type: static
  value: "public"

headers:                                   # ★ 请求头声明化
  x-opencode-client: "cli"
  x-opencode-project: "global"
  x-opencode-session: "ses_{{var:rid}}"    # 同请求复用
  x-opencode-request: "msg_{{var:rid}}"
  User-Agent: "{{ref:user_agent}}"

# convert_request 不再需要 → 从 scripts 移除，伪装逻辑全在 yaml
scripts:
  list_models: ./models.ts
```

config.yaml：

```yaml
upstreams:
  opencode-zen:
    user_agent: "opencode/1.15.0 ai-sdk/provider-utils/4.0.23 runtime/bun/1.3.13"
```

**对内核的要求**：

1. 转发引擎解析 `{{...}}` 模板：random/uuid 每请求生成；var 请求级作用域；ref 向插件管理器取 config 值；client_header 读入站请求头
2. 头合并顺序：auth 注入 → `special.headers.<协议>` → `headers` → convert_request（ts 还能最后覆盖，逃生舱）
3. 校验器：yaml 校验时检查模板语法合法性（占位符闭合、未知占位符报错）

### 5.7 上游可配置面（base_url / auth.static / body.defaults / network.proxy_pool）

> 2026-08-24 新增：**除了请求头，还有四个维度可能随平台/环境漂移**，都应声明进 yaml 可配置。
> 原则："这个值是否会随平台/环境漂移？会，就进 yaml 可配置；不会，就写死。"

**四类漂移维度**：

| 维度 | 场景（opencode zen） | 写死的后果 | 配置化字段 |
|---|---|---|---|
| **入口地址** | 免费模型 `/zen/v1/`、Go 套餐 `/zen/go/v1/` | 平台换域名/自建反代/内网镜像 → 改插件 | `base_url` |
| **认证形态** | key 是 `public`（匿名固定值） | 现有类型（bearer/header/query）套不上 | `auth.type: static` / `none` |
| **请求体默认参数** | 平台要求 `max_tokens` 等必传字段 | convert_request 写死 → 平台变更改 ts | `body.defaults` |
| **出口网络** | 免费模型按 IP 限速、muse-spark 禁 HK/SG | 无法绕 IP 维度限速/地区限制 | `network.proxy_pool` |

**字段说明**：

```yaml
# ① 入口地址（apis.path 是相对路径，host/前缀在这配）
base_url: "{{ref:zen_base_url}}"     # 静态直写 / {{ref:...}} 从 config.yaml 读

# ② 匿名/固定值认证（现有 bearer/header/query 之外新增）
auth:
  type: static                        # static = 固定值（如匿名 key "public"）；none = 完全无鉴权
  value: "public"                    # static 时用；也可 {{ref:...}}

# ③ 请求体默认字段注入（客户端显式传的值 > defaults）
body:
  defaults:
    max_tokens: 4096                 # 平台要求必传时声明，避免 convert_request 写死

# ④ 出口代理池（内核通用能力，任何上游可用）
network:
  proxy_pool: ref:resin-pool         # 按请求轮换出口 IP（绕 IP 限速 / 地区限制）
```

**两层可配置性边界**（避免过度设计）：

```
第 1 层：平台说明书（插件 yaml 可配置）—— 怎么连（端点/认证/头/默认参数）
第 2 层：内核机制（config.yaml 可配置）—— 怎么转发（重试次数/冷却时长/限流阈值/代理轮换策略）
```

- `base_url` / `auth` / `headers` / `body.defaults` / `network.proxy_pool` 引用 → 第 1 层（插件声明）
- 池的来源、轮换算法、冷却时长 → 第 2 层（config.yaml，内核执行）
- 判断标准：**值随平台漂移 → 插件 yaml；值随部署环境漂移 → config.yaml；两者都不漂移 → 写死**

**完整示例（opencode zen 上游，全可配置面）**：

```yaml
apiVersion: relayhub.io/v1
kind: Upstream-api-free
metadata:
  name: opencode-zen
  version: 1.0.0

base_url: "{{ref:zen_base_url}}"        # 默认 https://opencode.ai/zen/v1

apis:
  openai:    { path: /v1/chat/completions, method: POST }
  responses: { path: /v1/responses, method: POST }
  models:    { path: /v1/models, method: GET }

auth:
  type: static
  value: "public"

headers:                                 # 请求头声明化
  x-opencode-client: "cli"
  x-opencode-project: "global"
  x-opencode-session: "ses_{{var:rid}}"
  x-opencode-request: "msg_{{var:rid}}"
  User-Agent: "{{ref:user_agent}}"

body:
  defaults: { max_tokens: 4096 }

network:
  proxy_pool: ref:resin-pool

scripts:
  list_models: ./models.ts
```

config.yaml：

```yaml
upstreams:
  opencode-zen:
    base_url: "https://opencode.ai/zen/v1"
    user_agent: "opencode/1.15.0 ai-sdk/provider-utils/4.0.23 runtime/bun/1.3.13"
    proxy_pool:
      source: ref:resin-sub               # 代理池来源（resin 订阅转的节点列表）
      strategy: round-robin               # 轮换策略（round-robin / random / ip-hash）
```

**对内核的要求**：

1. `base_url` 与 `apis.path` 拼接为完整 URL；支持 `{{ref:...}}` 解析
2. `auth.type: static` / `none`：static 注入固定值（或模板），none 跳过鉴权段
3. `body.defaults` 合并：客户端显式字段优先，defaults 只补缺省
4. `network.proxy_pool`：内核连接层按策略轮换出口 IP（策略/池来源在 config.yaml）
5. 校验器：以上字段类型/引用合法性纳入 yaml 校验

## 7. 对内核的要求

### 7.1 插件管理器（新增核心模块）

- **上游定义管理**：加载 / 校验 / 热重载上游 yaml
- **凭据管理**：
  - 解析 `ref:` 引用 → 定位凭据源（**docker secret**：`/run/secrets/<name>`）
  - 加载进内存，不落盘、不写日志
  - 刷新生命周期：oauth-file 定时刷新（每 10m 检查，到期前 24h 刷新），刷新值只存内存
  - 轮换：重建容器换 secret，热生效
- **凭据注入**：向转发引擎提供"已解析的请求头集合"（模板 + 凭据值填充）

### 7.2 通用转发引擎

- 解析 yaml → 端点分发 → 向插件管理器取凭据 → 头注入 → **格式匹配** → 转发 → 响应回传
- 不感知凭据来源，只使用插件管理器给的请求头
- **格式匹配**：客户端格式 → 查模型 `capabilities` → 支持则直接转发，不支持则 400 报错（不做格式转换，见平台差异 §2.5）
- **请求头模板解析**：解析 `headers` / `special.headers` 里的 `{{...}}` 占位符
  （random/uuid/var/ref/client_header，见 §5.6），生成请求级动态值
- **入口拼接**：`base_url` + `apis.path` 拼完整 URL（见 §5.7）
- **请求体默认值合并**：`body.defaults` 只补缺省，客户端显式字段优先（见 §5.7）
- **出口代理轮换**：按 `network.proxy_pool` 引用向插件管理器取池，按 config.yaml 策略轮换出口 IP（见 §5.7）

### 7.3 参数修正（2026-08-24 简化：不做格式转换）

- **格式匹配**：客户端格式 → 查 `capabilities` → 支持/报错（内核职责，不做转换）
- **参数修正**：`convert_request/convert_response`（插件 TS 钩子，同格式内修正平台怪癖）
- 上游支持客户端格式 → 零修正直接转发；有怪癖 → 插件写 TS 钩子
- 特殊上游（逆向类）→ TS 钩子实现，不需要改内核

### 7.4 其他

1. **配置热重载**：上游 yaml / 凭据变更不重启（`SIGHUP` 或 watch）
2. **校验器**：启动时校验 yaml（auth 字段完整性、apis 路径、scripts 引用的文件存在、ref 指向的凭据存在）

## 8. 与插件架构决策的关系

- 本设计是"进程内插件"第一层的具体化：**上游适配器 = YAML 声明 + TS 钩子**
- 特殊上游（逆向类，如 sub2api 的 grok 伪装）→ 写 TS 钩子（convert_request/response），
  普通上游 → 零代码 yaml
- 仍然不需要：独立容器、wasm、go plugin

## 9. 上游定义版本管理（Cargo / SemVer 规则）

> 用户 2026-08-21 提出：插件版本写在**目录名**里（`openai-1.0.0/`）。
> 用户 2026-08-22 升级：**版本号统一按 Cargo/SemVer 规则**（三级 + 预发布 + 约束符号，见 [插件开发规范 §1.4](../插件开发规范.md)）。

### 9.1 命名约定（目录式，非单文件）

```
插件包目录：<name>-<version>/
  openai-1.0.0/upstream.yaml
  openai-1.1.0/upstream.yaml
  codex-cpa-2.3.0/upstream.yaml
  anthropic-0.9.0/upstream.yaml     # 0.x 预发布语义（不稳定）
  openai-1.2.3-beta.1/              # 预发布版本（不参与常规解析）
```

**为什么版本进目录名**：

| 收益 | 说明 |
|---|---|
| 多版本天然并存 | 文件系统允许同名不同版本同时存在，无需覆盖 |
| 目录列表即版本清单 | `ls` 一眼看到所有可用版本，无需读内容 |
| 回滚 = 改引用 | 旧版本目录还在，config.yaml 改回 `@旧版本` 即可 |
| 灰度 = 双引用 | 同名上游两个版本同时启用，路由按权重分流 |
| 与 Cargo 版本目录同构 | 部署经验直接复用（`<name>-<version>/` 风格） |

### 9.2 文件内结构（与真实插件一致，无 spec 包装）

```yaml
# openai-1.0.0/upstream.yaml
apiVersion: relayhub.io/v1     # schema 版本（对应转换器接口大版本）
kind: Upstream-api-balance     # 三级 kind（凭据 × 计费）
metadata:
  name: openai                 # 资源名（必须与目录名 <name> 一致）
  version: 1.0.0               # ← Cargo/SemVer 三级，必须与目录名版本一致（I6 校验）
  labels:                      # 可选，用于分组/筛选
    vendor: openai
depends:
  kernel: "^0.1"               # Cargo 依赖声明（见插件开发规范 §1.5）
# 其余字段（auth / apis / special / scripts 等，见 §5.x 草案）直接平铺，无 spec 包装
```

**apiVersion 语义**（K8s 风格）：

| apiVersion | 含义 |
|---|---|
| `relayhub.io/v1` | 稳定 schema，向后兼容（字段只增不减） |
| `relayhub.io/v1beta1` | 实验特性，可能 breaking change |
| `relayhub.io/v2` | schema 大版本演进（对应转换器接口大版本） |

> apiVersion 与目录名版本**解耦**：
> - 目录名版本 = 上游定义的迭代版本（openai 协议适配的小步演进）
> - apiVersion = schema / 转换器接口的兼容性契约（字段结构的 breaking change）
> 转换器接口升级 breaking 时 → 新 apiVersion；普通改协议细节 → 目录名版本 +1。

### 9.3 config.yaml 引用（Cargo 约束符号）

```yaml
upstreams:
  - ref: openai@^1.0         # name@约束，类似 Cargo 依赖（解析到 >=1.0,<2.0 最新）
  - ref: openai@1.1.0        # 精确版本（=1.1.0）
  - ref: codex-cpa@~2.3      # >=2.3,<2.4（只允许 patch/minor 更新）
  - ref: anthropic@0.9.0     # 预发布需显式指定
```

- `ref` 由插件管理器解析：`name@约束` → 定位到满足约束的 `<name>-<version>/` 目录
- 约束符号 = Cargo VersionReq（`^`/`~`/`=`/区间/通配，见插件开发规范 §1.4）
- 精确版本 = 锁定；约束版本 = 解析到约束内最高版本，实际版本记入 `relayhub.lock`（I5）
- 切换版本 = 改 `ref`，热重载生效；回滚 = 改回旧约束
- 同名不同版本并存（灰度）= 两个 `ref` 引用不同约束/版本，路由按权重分流

### 9.4 校验规则

- **目录名**必须匹配 `<name>-<version>`（semver 三级）
- `metadata.name` 必须与目录名 `<name>` 一致（I6）
- `metadata.version` 必须与目录名 `<version>` 一致（I6）
- 同一 `name` 的多版本目录可共存；config.yaml 引用的版本必须存在
- `apiVersion` 必须被当前内核支持（否则拒绝加载）

### 9.5 与 K8s 的对照

| K8s | RelayHub |
|---|---|
| `image: nginx:1.25.3` | `ref: openai@1.0.0` |
| Helm chart 目录 `mychart-1.0.0/` | 插件目录 `openai-1.0.0/` |
| `apiVersion: apps/v1` | `apiVersion: relayhub.io/v1` |
| Deployment rollout / rollback | 改 ref + 热重载（回滚 = 改回旧版本号） |
| 多版本并存灰度 | 同名多 ref 并存按权重分流 |
| Canary / 权重分流 | `ref` 带 weight 字段（见 9.6） |
| 就绪探针 readinessProbe | `/healthz` 端点（金丝雀判定） |

### 9.6 灰度规则（借鉴 K8s 编排心智）

> 用户 2026-08-21 确认：灰度这些规则就是借鉴 K8s 的思路。
> 原则：**只借 K8s 的编排心智模型（rollout / canary / weight / readiness），
> 不引入 K8s 基础设施**（自写轻量实现）。

#### 灰度权重声明（config.yaml）

```yaml
upstreams:
  - ref: openai@1.0.0
    weight: 90            # 旧版本 90% 流量
  - ref: openai@1.1.0
    weight: 10            # 新版本 10% 流量（金丝雀）
    canary: true          # 标记金丝雀（可选）
```

#### 灰度流程（借鉴 K8s rollout）

```
1. 新版本 openai-1.1.0/ 目录放入插件目录
2. config.yaml 加 ref，weight 设 10%（金丝雀）
3. 热重载生效 → 10% 请求走新版本
4. 观察：/healthz 就绪 + 错误率/延迟指标（relayhub status 命令）
5. 逐步上调 weight：10% → 50% → 90% → 100%
6. 稳定后：移除旧版本 ref，删除 openai-1.0.0/ 目录
7. 异常：下调 weight 或改回旧 ref（回滚）
```

#### 灰度判定的支撑

| K8s 机制 | RelayHub 对应 |
|---|---|
| readinessProbe | `/healthz`（就绪探针端点，内核必须提供） |
| 指标观察 | `relayhub status` 命令（错误率/延迟/各版本流量） |
| rollout 进度 | config.yaml weight 逐步调整 + 热重载 |
| rollback | 改回旧 ref / 下调 weight |

#### 与"容器金丝雀升级"的关系

- **容器层金丝雀**（3.5 决策）：升级 RelayHub 镜像本身时，新旧容器滚动
- **上游层金丝雀**（本节）：RelayHub 运行时，切换上游定义版本时灰度
- 两者是同一心智模型（canary + weight + readiness）在不同层级的应用

#### 灰度自动回退（既定决策 2026-08-21）

> 用户确认：**灰度新版本如果报错，默认回退旧版本**。

**自动回退规则**：

- 新版本（canary）报错 → 自动回退到旧版本（前一稳定版本）
- 触发条件：新版本错误率达到阈值（如连续 N 个 5xx / 错误率 > X%）
- 回退动作：路由权重自动切回旧版本（新版本 weight → 0）
- 日志/状态：`relayhub status` 记录回退事件，便于复盘

**设计原则**：

1. **默认保守**：金丝雀异常时宁可全走旧版本，不让用户流量受损
2. **阈值可配置**：`canary.auto_rollback.threshold` 可在 config.yaml 声明
3. **回退不删版本**：新版本文件保留，修复后可重新灰度（类似 K8s rollout 暂停）

```yaml
upstreams:
  - ref: openai@1.0.0
    weight: 90
  - ref: openai@1.1.0
    weight: 10
    canary:
      auto_rollback: true
      threshold:                # 触发回退的阈值
        error_rate_5xx: 0.05    # 5xx 错误率 > 5%
        consecutive_failures: 5 # 或连续 5 次失败
```

## 10. 热重载并发安全：通过设计解决（既定决策）

> 用户 2026-08-21 提出：热重载时在途请求的处理，**通过设计来解决**——
> 理论上不会出现（在途请求不受重载影响）。
> 方案：**copy-on-write（写时复制）不可变快照 + 原子指针替换**。

### 10.1 核心机制

```rust
// 配置快照是不可变对象，构造后不再修改
static UPSTREAMS: AtomicPtr<UpstreamTable> = AtomicPtr::new(null_mut());  // 原子指针，读路径无锁

// 每个请求处理开始时，快照一次指针
let snapshot = UPSTREAMS.load(Ordering::Acquire);   // 拿到当前配置的不可变快照

// 重载时：构造新快照（完全新对象），原子替换指针
let new_table = Box::into_raw(Box::new(build_table(new_config)));  // 新快照（旧快照不受影响）
UPSTREAMS.store(new_table, Ordering::Release);                     // 替换指针
```

### 10.2 为什么在途请求天然安全

- 请求 A 在重载前 `load()` 了旧快照 → 整个请求生命周期用旧配置（路由表、scripts 钩子、凭据引用）
- 重载只是 `store()` 新快照 → 不影响请求 A 已持有的旧快照引用
- 旧快照在最后一个引用它的请求结束后被回收（Rust 所有权/引用计数，无泄漏）
- **在途请求与重载天然隔离**：不需要锁、不需要排空、不需要等待

### 10.3 需要遵循的设计约束（写进内核）

1. **快照不可变**：快照构造后禁止修改（构建时完成所有解析/校验）
2. **请求全程用快照**：请求 handler 从进入就 `Load()` 一次，全程用这一个快照（不中途重取）
3. **凭据引用也是快照**：凭据解析结果包含在快照内（oauth-file 刷新是独立于快照的内存对象）
4. **重载失败不替换**：新配置校验失败 → 丢弃新快照，保留旧快照（原子性）

### 10.4 边界情况

| 场景 | 处理 |
|---|---|
| 重载失败 | 校验失败丢弃新快照，旧配置继续生效（日志告警） |
| 重载期间到达的请求 | 用旧快照（Load 发生在 Store 前）或新快照（Load 在 Store 后），两者都完整可用 |
| 配置引用的一致性 | 快照内所有引用（ref/credentials/scripts）在构建时验证，不存在悬空引用 |

### 10.5 结论

> 用户判断正确：**热重载与在途请求的冲突，通过 copy-on-write 设计在理论上就不存在**。
> 内核实现时只需遵守"快照不可变 + 请求全程用同一快照"两条约束。
