# 模型映射与模型列表设计

> 设计文档：RelayHub 的模型映射（model mapping）与对外 /v1/models 模型列表接口。
> 调研基础：one-api / new-api / simple-one-api / litellm / sub2api / Portkey 六个中转站源码实证。
> 核心原则：**映射数据跟着插件走（yaml 声明），解析行为跟着内核走（resolver/handler）**。

---

## 1. 调研结论总览

| 项目 | 映射配置位置 | 映射粒度 | 列表数据来源 | 列表过滤/缓存 | 渠道-模型索引 |
|---|---|---|---|---|---|
| **one-api** | DB `channels.model_mapping`(JSON) | 渠道级 | 启动静态聚合各 adaptor 常量 | 按分组过滤 + Redis 缓存 | `abilities` 表 |
| **new-api** | DB 同上 | 渠道级 | 静态聚合 + UniqBy | 分组/token限制/计费过滤 | `abilities` 表 + weight/tag |
| **simple-one-api** | config.yaml `model_map`/`model_redirect` | 服务级+全局 | 启动构建内存 supportModels | 无（map 去重） | 内存 `modelToService` |
| **litellm** | 全局 alias + router group alias + DB team alias | 全局/路由组/团队 | router.model_list + alias 展开 + wildcard 探测 | key→team→proxy 级联 + 健康过滤 | `model_name_to_deployment_indices` |
| **sub2api** | DB 渠道 `model_mapping[platform]` + 账号级 + 分组级 | 渠道/账号/分组 | 聚合账号 model_mapping keys | gocache 短 TTL 缓存 | 调度器选号 |
| **Portkey** | 无（控制面 ALBUS） | — | 纯透传上游 | 无 | 无 |

**共性发现**：
1. 映射都发生在**渠道选定之后、转发之前**（查表替换 model 字段）
2. 计费/日志用**原始模型名**，转发用**映射名**（one-api 明确分离）
3. 模型列表 = 模型白名单/映射 key 的聚合（非独立实体）

## 2. 模型映射设计（RelayHub）

### 2.1 核心模式：数据在插件，行为在内核

```
upstream.yaml（插件声明数据）             内核（解析行为）
─────────────────────                   ─────────────────
model_map:                              ModelResolver 接口
  gpt-4o: gpt-4o-2024-11-20             Resolve(ctx, model) → (upstreamModel, mapped, err)
  claude: claude-sonnet-4               （渠道选定后、转发前调用）
```

**为什么**：换插件不换内核——`model_map` 是插件声明（数据），`ModelResolver` 是内核能力（行为）。

### 2.2 内核 ModelResolver（抄 new-api + sub2api）

| 能力 | 参考 | 说明 |
|---|---|---|
| 链式解析 | new-api `model_mapped.go` | `a→b→c` 取链尾 |
| 循环检测 | new-api | `model_mapping_contains_cycle` 报错 |
| 通配符前缀 | sub2api `wildcardMappingByGP` | `"grok-*"` 前缀匹配 |
| IsMapped 标记 | new-api | 计费/日志用原名，转发用映射名 |

```rust
pub trait ModelResolver {
    /// 渠道选定后、转发前调用。返回上游实际模型名 + 是否发生过映射。
    fn resolve(&self, ctx: &RequestCtx, model: &str) -> Result<(String, bool), ResolveError>;
}
```

**管道位置**：`选渠道 → ModelResolver.resolve() → convert_request → 转发`

### 2.3 插件声明（upstream.yaml）

```yaml
# upstream.yaml
model_map:                    # 外部名 → 上游名（渠道级映射）
  gpt-4o: gpt-4o-2024-11-20
  claude: claude-sonnet-4
  "grok-*": "grok-4-"         # 通配符前缀（可选）
model_redirect:               # 全局重定向（可选，simple-one-api 的全局层）
  "gpt-5.6": "gpt-5.6-sol"
```

**映射粒度**（RelayHub 取舍）：
- ✅ 上游插件级（`upstream.yaml` 的 model_map）—— 对应 simple-one-api 服务级
- ✅ 全局 redirect（可选）—— 对应 simple-one-api 全局层
- ❌ 团队级 alias（litellm）—— 超出自用定位
- ❌ DB 字段（one-api）—— RelayHub 无 DB

## 2.5 对外模型命名：`<上游名>_<模型名>`（既定 2026-08-21）

> 用户确认：从上游获取模型列表后，对外发布时用 **`<上游名>_<模型名>`** 格式。
> 分隔符分层：`_` = 上游分隔（唯一）、`-` = 模型名内部（归一化产物）。
> **`_`→`-`、`/`→`-` 归一化方案**（2026-08-21 用户优化 + 2026-08-25 补 `/`）：
> 模型名从上游获取后把 `_` 和 `/` 都转成 `-`，插件名规范也不用 `_` → **`_` 是唯一分隔符，模型名不含 `_` 和 `/`，拆解零歧义**。

### 2.5.1 为什么加前缀

| 问题 | 前缀解决 |
|---|---|
| 多个上游有同名模型（多个平台都有 gpt-4o） | ✅ 上游前缀命名空间，无冲突 |
| 用户不知道模型来自哪个平台 | ✅ 一眼看出上游 |
| 路由时不知道发给谁 | ✅ 前缀即上游标识 |

### 2.5.2 命名规范化规则（`_`→`-`、`/`→`-` 归一化）

```
核心原则：`_` 是唯一分隔符（上游名↔模型名），模型名不含 `_` 和 `/` → 拆解无歧义
```

**三层命名规范**：

| 层 | 规范 | 例子 |
|---|---|---|
| 插件名 | 不含 `_`（用 `-` 或字母） | `opencode-go`、`tokenrhythm` |
| 模型名（规范化） | 上游 `_`、`/` → `-` | `qwen_3.5_max` → `qwen-3.5-max` |
| 对外分隔符 | `_`（唯一含 `_` 的地方） | `tokenrhythm_qwen-3.5-max` |

```
对外名 = 插件名 + "_" + normalize(模型名)
  opencode-go + deepseek_v4_flash_0731 → opencode-go_deepseek-v4-flash-0731
  tokenrhythm + qwen_3.5_max           → tokenrhythm_qwen-3.5-max
```

模型名规范化（normalize）：所有 `_` → `-`、所有 `/` → `-`；其他字符按需清理。
★ **在 models.ts 的 list_models 钩子内做**（2026-08-24 确认），内核不做归一化。
模型名来源：上游 `/v1/models` 返回的原始 id。
★ **归一化名只是键**：上游原始 id 存 `ModelInfo.raw_id`（§3.2.1），转发请求 / `model_map` 匹配 / L7.3 匹配一律用 raw_id，**不从归一化名反推**（如 OpenRouter `meta-llama/llama-3.1-8b` → id `meta-llama-llama-3.1-8b` + raw_id `meta-llama/llama-3.1-8b`）。

### 2.5.3 反向解析（客户端请求 → 路由）—— 按 `_` 拆，无歧义

```
resolve("tokenrhythm_qwen-3.5-max")
  → 按第一个 "_" 拆：插件名 "tokenrhythm" + 模型名 "qwen-3.5-max"
  → 前缀查注册表：tokenrhythm 是已知上游 ✅
  → 模型名 qwen-3.5-max（含 - 完全 OK，因为拆解只认 _）
  → 转发时用 raw_id 请求上游（如有 model_map 先映射）
```

**为什么无歧义**：`_` 是独占分隔符——两侧规范化后都不含 `_` 和 `/`，所以**直接按 `_` 拆分即可**，不需要前缀注册表/最长匹配。

**解析顺序（最终版）**：
1. 完整匹配 `model_map`（用户显式映射优先）
2. 按 `_` 拆解（默认规则，无歧义）
3. 失败 → 错误"未知模型"

### 2.5.4 边界情况处理

| 场景 | 处理 |
|---|---|
| 模型名含 `_`（`qwen_3.5_max`） | ✅ 规范化 `_`→`-`（`qwen-3.5-max`），不冲突 |
| 模型名含 `/`（OpenRouter `meta-llama/llama-3.1-8b`） | ✅ 规范化 `/`→`-`（`meta-llama-llama-3.1-8b`）；**原始 id 存 raw_id 不丢** |
| 模型名含 `-`（`deepseek-v4-flash`） | ✅ 保留（拆解只认 `_`，`-` 无影响） |
| 插件名带 `-`（`opencode-go`） | ✅ 保留（前缀含 `-` 无影响） |
| 模型名恰好以某上游名开头 | 显式 `model_map` 覆盖 |
| 规范化冲突（`a_b` 和 `a-b` 归一化同名） | 聚合时检测，报错或后者覆盖 |

### 2.5.5 模型列表定时刷新（2026-08-24 更新：models.ts → models.yaml）

> 用户确认：**模型列表每 30 分钟自动更新一次**，并给内核加**手动刷新命令**。
> 2026-08-24 更新：**models.ts 刷新 models.yaml，内核读 models.yaml**（不每次调 ts）。

```
定时刷新：每 30 分钟
  → 内核调各插件 list_models 钩子（ts）
  → 钩子内：拉上游 /v1/models + _→-、/→- 归一化 + 返回 ModelInfo[]（含 raw_id）
  → 内核把结果写回插件包内 models.yaml（快照）
  → 内核读 models.yaml 聚合 + 前缀拼接 → 对外 /v1/models

手动刷新：relayhub models refresh（内核命令）
  → 同上，立即触发
```

**实现要点**：
- 定时任务由内核调度（类似凭据刷新调度）
- 刷新失败保留旧 models.yaml（静默降级，记录日志）
- 手动命令可强制跳过 TTL
- ★ **models.yaml 放插件包内**（`<插件名>-1.0.0/models.yaml`），刷新直接改插件包文件
- ★ **归一化在 models.ts 做**（钩子返回时模型名已 `_`→`-`、`/`→`-`），内核不做归一化，只按 `/`、`_` 拆分
- ★ **内核启动时优先读 models.yaml**（快，不调 ts）；models.yaml 不存在时才调 list_models 生成

### 2.5.6 与 model_map 的关系

```
用户显式 model_map（别名）       vs      默认前缀规则
  gpt-4o: opencodego_gpt4o                opencodego_gpt4o
  短名，用户自定义                       自动生成，无冲突
  优先级：显式映射优先                     兜底
```

- **显式映射**：用户想用短名/别名时配 `model_map`（如 `gpt-4o` 指到某个上游）
- **默认规则**：不配映射时，对外名自动是 `上游名_模型名`

## 3. 对外 /v1/models 模型列表设计

### 3.1 内核标准 handler + 插件注册模型来源

内核实现 `GET /v1/models`（OpenAI 标准格式），模型来源抽象成 `ModelListProvider`：

| Provider | 数据来源 | 参考 | 适用 |
|---|---|---|---|
| `static` | 读插件包内 `models.yaml`（声明文件，由 probe 生成/刷新） | simple-one-api | 默认，0 成本 |
| `aggregate` | 聚合已启用 upstream 的 `models.yaml` | one-api abilities 聚合 | **RelayHub 默认推荐** |
| `probe` | 调 `list_models` 钩子（ts）探测上游 `/v1/models`，结果写入 `models.yaml` | litellm wildcard、sub2api gocache | 定时/手动刷新 |

> ★ **models.yaml 是 probe 的产物、static/aggregate 的数据源**（2026-08-24）：
> - probe 生成 models.yaml（调 models.ts）
> - static 读 models.yaml（不调 ts，快）
> - aggregate 聚合多个 models.yaml
> - 内核启动时优先读 models.yaml，不存在时才调 list_models 生成

### 3.2 三态递进（声明 → 聚合 → 探测）

```
static（声明态）→ aggregate（聚合态）→ probe（探测态）
  yaml 白名单       多插件模型并集        真请求上游验证
  零成本            默认推荐             可选增强，不做就零成本
```

### 3.2.1 模型能力：每个模型支持什么协议（既定 2026-08-22）

> 用户澄清：**内核认 4 种格式（入口），但每个模型支持什么格式由上游模型列表决定**，
> 发布的模型列表也要**标明每个模型支持什么格式**。

**两个维度分开**：

| 维度 | 含义 | 决定者 |
|---|---|---|
| **入口格式** | 客户端能用什么格式调 RelayHub | 内核（认 4 种：openai/anthropic/responses/gemini） |
| **模型能力** | 这个模型（上游）实际支持哪些协议 | **上游模型列表**（`supports_anthropic`/`supports_responses` 等） |

**ModelInfo 契约**（2026-08-25 定稿：主结构固定 + 子结构自定义）：

> ★ 主结构 = 顶层 11 键，**所有插件 models.yaml 统一标准**（不许增删顶层键）。
> ★ **子结构** = RelayHub 自定义（参考各上游扩展字段语义，但**不绑定任何一家**）：
>   上游返回什么映射成什么，缺了不硬填；缺失字段留给 Kernel-models 用其他源补全。
> ★ 主结构分三层：路由键（id/raw_id）→ 能力（capabilities）→ 按需（其余 9 键）。
> ★ **无 pricing**（2026-08-25 用户拍板）：RelayHub 只转发，计价由上游/中转站自己算，
>   models.yaml 不存单价；若未来有计费需求，由计费插件自己对接上游，不进本契约。

```ts
interface ModelInfo {
  // ═══ ① 路由键（必填）════════════════════════════════════
  id: string                     // 对外模型 ID（★ 已归一化 _→-、/→-，内核直接用）
  raw_id: string                 // ★ 上游原始 ID（不归一化）
                                 //   转发请求 / model_map 匹配 / L7.3 与 OpenRouter 匹配都用它

  // ═══ ② 能力（必填）══════════════════════════════════════
  capabilities: {
    // —— 协议维度（必填，客户端用什么格式调）——
    openai: boolean              // 支持 OpenAI /v1/chat/completions 格式
    anthropic: boolean           // 支持 Anthropic /v1/messages 格式
    responses: boolean           // 支持 OpenAI /v1/responses 格式
    gemini: boolean              // 支持 Gemini generateContent 格式
    // —— 输入模态（可选）——
    vision?: boolean             // 图片输入
    audio?: boolean              // 音频输入
    video?: boolean              // 视频输入
    file?: boolean               // 文件输入
    // —— 输出模态（❌ 暂不定义）——
    // imageOutput/audioOutput 等生图/音视频输出：当前全是文字模型，
    // 未来做 image/audio/video/mix 模态 kind 时再补（见插件模板分类 §0.1）
    // —— 功能（可选）——
    thinking?: boolean           // 推理/思考
    tools?: boolean              // 工具调用
  }

  // ═══ ③ 按需字段（9 键，缺了不硬填）═════════════════════
  displayName?: string           // 展示名（页面插件展示用，如 "OpenAI: GPT-5.6"）
  description?: string           // 模型描述（页面插件展示用）

  limits?: {
    context?: number             // 最大上下文 token 数
    maxOutput?: number           // 最大输出 token 数
  }

  supportedParameters?: string[] // 客户端可传参数名（如 ["tools","temperature"]，开放不枚举）

  defaultParameters?: {          // 参数默认值（键开放；null = 无默认值，≠ 0）
    [param: string]: number | string | boolean | null
  }

  reasoning?: {                  // 推理/思考详细配置
    mandatory: boolean           // 是否强制开启推理（不能关）
    defaultEnabled?: boolean     // 默认是否开启
    supportedEfforts?: string[]  // 支持等级（如 ["max","high","medium","low"]）
    defaultEffort?: string       // 默认等级
  }

  knowledgeCutoff?: string       // 知识截止日期（如 "2026-02-16"）
  expirationDate?: string        // 模型下线日期（免费模型限时，K8）
}
```
**上游字段 → 本契约的映射规则**（2026-08-25）：

1. **主结构 11 键固定**：所有插件 models.yaml 统一，不许增删顶层键
2. **子结构如实映射**：上游有就填、没有就不填（**缺了不硬填、不补假值**）
3. **不映射不序列化**：无关字段（pricing/created/aliases/benchmarks/supportedVoices/perRequestLimits/isModerated/tokenizer/instructType/modality）不进 models.yaml
4. **参考实现**：openrouter 插件 `models.ts`（唯一"插件即元数据源"，直接产出完整主结构）

> ⚠️ **models.yaml 持久化分组**（2026-08-25）：契约全量 ≠ 每个插件都填。
> models.yaml 只序列化**主结构（内核消费字段）**，分组如下：

| 分组 | 字段 | 内核用途 | 必填？ |
|---|---|---|---|
| 路由键 | `id` / `raw_id` | 对外名 / 上游原始 ID（转发用） | ✅ 必填 |
| 能力 | `capabilities` | 格式匹配 + 路由（协议/模态/功能） | ✅ 必填 |
| 展示 | `displayName` / `description` | 页面插件展示 | 按需 |
| 限制 | `limits` | context / maxOutput | 按需 |
| 参数 | `supportedParameters` / `defaultParameters` | 客户端可传参数 | 按需 |
| 推理 | `reasoning` | 思考详细配置 | 按需 |
| 生命周期 | `knowledgeCutoff` / `expirationDate` | 免费模型限时下线（K8） | 按需 |

> ❌ **不持久化**（不映射、不序列化）：`pricing` / `created` / `aliases` / `benchmarks` / `supportedVoices` / `perRequestLimits` / `isModerated` / `tokenizer` / `instructType` / `modality` —— 无关，白占体积。
> 计费（pricing）归上游/中转站自己算，RelayHub 只转发不计价（2026-08-25 用户拍板）。
>
> 本节为唯一权威；[插件模板分类 §0.7](./插件模板分类.md) 仅保留定位说明，不重复本表。

> ⚠️ **字段来源**（2026-08-24，基于 OpenRouter 422 模型全量统计）：
> - **插件 list_models 填**：协议维度（最权威，平台返回什么填什么）
> - **Kernel-models 从 OpenRouter 补全**：能力维度 + limits + supportedParameters + defaultParameters + reasoning + benchmarks
> - **计价由上游/中转站自己算**：RelayHub 只转发，不存储/不计算 pricing（2026-08-25 用户拍板）
> - **内核生成对外 /v1/models 时**：全部字段都支持（可选择性展示），不能没有
>
> 详见 [analysis/06-commercial-reference/openrouter](../../../analysis/06-commercial-reference/openrouter/openrouter.md) §1.2。

**模型能力数据流**：

```
上游 /v1/models（原始）
  → list_models 钩子归一化：ModelInfo（id + capabilities + limits）
  → 内核聚合 + 前缀命名 + 元数据补全（见 §3.2.2）
  → 对外 /v1/models 标明每个模型的 capabilities（客户端可查）
```

**对外模型列表带能力标记**：

```json
{
  "object": "list",
  "data": [
    {
      "id": "tokenrhythm_gpt-4o",
      "object": "model",
      "owned_by": "tokenrhythm",
      "raw_id": "gpt-4o",              // 内部字段，不对外暴露（此处仅示意）
      "capabilities": { "openai": true, "anthropic": false, "responses": false, "vision": true, "tools": true },
      "limits": { "context": 128000, "maxOutput": 16384 }
    }
  ]
}
```

**能力的作用**（2026-08-24 更新：格式匹配+报错，不做转换）：
1. **路由时**：客户端用 anthropic 格式请求某模型 → 查该模型 `capabilities.anthropic` → **支持则直接转发，不支持则 400 报错**（不做格式转换）
2. **客户端选择**：客户端看 /v1/models 知道哪个模型能用哪个协议调
3. **协议选择**：`protocols.preferred` 是平台级默认，`capabilities` 是模型级事实——**模型级优先**

> ⚠️ **不做格式转换**（2026-08-24 架构简化）：客户端格式与上游不匹配时直接报错，
> 不做 openai↔anthropic 互转。用户需要跨格式调用时，自行加本地转换插件或用 ccswitch 等工具。
> 这与 OpenRouter / one-api / new-api 的做法一致。

> 这正对应 tokenrhythm 实测：`qwen3.7-max` 的 `supports_anthropic=false`（模型级），
> 不是平台整体不支持，而是特定模型不支持。

### 3.2.2 模型元数据补全（2026-08-24 新增）

> 插件 `list_models` 能填的能力字段有限（平台返回什么填什么），缺失的字段由内核补全。

**补全数据源**（优先级从高到低）：

| 数据源 | URL | 补全字段 | 说明 |
|---|---|---|---|
| **插件 list_models** | 上游 `/v1/models` | 协议维度（openai/anthropic/responses） | 插件归一化，最权威 |
| **OpenRouter** | `https://openrouter.ai/api/v1/models` | 能力维度 + limits | 字段最全（`architecture.input_modalities`/`supported_parameters`/`reasoning`/`context_length`） |
| **models.dev** | opencode 模型目录 | 能力维度 + limits + 价格 | 模型 ID 更接近原始名 |

**OpenRouter 字段映射**：

| OpenRouter 字段 | → ModelInfo 字段 | 判定 |
|---|---|---|
| `architecture.input_modalities` 含 `"image"` | `capabilities.vision` | `true` |
| `architecture.input_modalities` 含 `"audio"` | `capabilities.audio` | `true` |
| `architecture.input_modalities` 含 `"video"` | `capabilities.video` | `true` |
| `supported_parameters` 含 `"tools"` | `capabilities.tools` | `true` |
| `reasoning` 存在 | `capabilities.thinking` | `true` |
| `context_length` | `limits.context` | 直接取值 |
| `top_provider.max_completion_tokens` | `limits.maxOutput` | 直接取值 |

**关键问题：模型 ID 映射**（2026-08-24 实测验证）：
OpenRouter 的 ID 是 `provider/model` 格式，上游的 ID 是 model 部分。
**匹配策略**：忽略 `/` 前部分（provider 前缀），用 model 部分精确匹配。
实测 tokenrhythm 17 模型中 15 个精确匹配，2 个无匹配（OpenRouter 未收录）。
边界：`:batch`/`:free` 后缀需剥离后匹配基础名；无匹配时只输出上游字段不阻塞。

**补全流程**（Kernel-models 插件，H9/G5）：

```
插件 list_models 返回 ModelInfo（部分字段）
  ↓
Kernel-models 按 ID 匹配 OpenRouter / models.dev 数据
  ↓
合并：插件数据优先（权威），补全缺失字段
  ↓
对外 /v1/models 输出完整 ModelInfo
```

> ⚠️ 补全是**尽力而为**：匹配不到外部数据源时，只输出插件提供的能力字段，不阻塞。

### 3.2.3 models.yaml 文件（2026-08-24 新增：模型列表声明/缓存文件）

> **models.ts 刷新 models.yaml，内核读 models.yaml**（用户 2026-08-24 确认）。
> models.yaml 是 probe 的产物、static/aggregate 的数据源。

**位置**：插件包内 `<插件名>-1.0.0/models.yaml`（刷新直接改插件包文件）

**生成方式**：内核调 `list_models` 钩子 → 钩子返回 `ModelInfo[]`（已归一化）→ 内核序列化写入 models.yaml

**文件格式**（ModelInfo[] 的 YAML 序列化）：

```yaml
# <插件名>-1.0.0/models.yaml（由 models.ts 的 list_models 生成，勿手改）
# 刷新时间：2026-08-24T12:00:00Z
models:
  - id: hy3-free                    # ★ 已归一化（_→-、/→-），内核直接用
    raw_id: hy3-free                # ★ 上游原始 ID（转发时用，不归一化）
    capabilities:
      openai: true
      anthropic: false
      responses: false
      vision: false
      thinking: true
      tools: true
    limits:
      context: 262144
      maxOutput: 128000
  - id: mimo-v2.5-free
    capabilities:
      openai: true
      anthropic: false
      responses: false
      vision: false
      thinking: false
      tools: true
    limits:
      context: 1048576
      maxOutput: 131072
```

**读取优先级**（内核启动时）：
1. 读插件包内 `models.yaml`（快，不调 ts）→ 有则用
2. `models.yaml` 不存在 → 调 `list_models` 钩子生成 → 写入 `models.yaml`
3. 定时/手动刷新 → 调 `list_models` 钩子 → 更新 `models.yaml`

**与 upstream.yaml 的关系**：
- `upstream.yaml` 的 `apis.models`：声明上游 `/v1/models` 端点路径（给钩子用）
- `models.yaml`：模型列表数据（给内核读）
- 两者独立：`upstream.yaml` 是规则，`models.yaml` 是数据

### 3.3 内核 handler 职责

1. **标准格式**：`{"object":"list","data":[{id,object,created,owned_by,capabilities}]}`（OpenAI）
2. **前缀命名**：列表中的 id = `<上游名>_<模型名>`（§2.5 规则），`owned_by` = 上游名
3. **能力标记**：每个模型带 `capabilities`（§3.2.1），标明支持哪些协议，来自上游模型列表
4. **去重 + 排序**：map + key 排序（simple-one-api 模式）；规范化冲突时后者报错或后者覆盖
5. **可选可用性过滤**：合并健康检查，隐藏不健康 upstream 的模型（litellm `healthy_only` 轻量版）
6. **缓存**：内存快照 + TTL（sub2api `modelsListCache`），插件变更时主动失效
7. **random 模型**（可选）：simple-one-api 的 `random` 额外模型

### 3.4 展示与调度分离

> sub2api 的 `GroupModelsListConfig` 思路：**模型列表可自定义展示，不影响实际路由**。
> RelayHub 的模型列表只是"给客户端看有哪些可用模型"，实际路由由路由策略决定，两者解耦。

### 4.1 upstream.yaml 新增字段

```yaml
models:                       # 通用端点（列表接口用，已有）
  path: /v1/models
  method: GET
model_map:                    # 新增：模型映射（见 §2.3）
  gpt-4o: gpt-4o-2024-11-20
models_whitelist:             # 新增：模型白名单（static provider 用）
  - gpt-4o
  - claude-sonnet-4
```

### 4.2 list_models 钩子的职责定位

调研后明确：`list_models` ts 钩子 = **probe 模式的实现**（真请求上游 /models 并归一化）。
而默认的 `aggregate`/`static` 模式不需要 ts——内核直接从 yaml 聚合。

```
static / aggregate → 内核纯 yaml 聚合（不需要 list_models 钩子）
probe              → 需要 list_models 钩子（ts 实现探测 + 归一化）
```

## 5. 避免做的事（调研教训）

| 不做 | 原因 |
|---|---|
