# 平台差异与协议兼容处理

> 设计记录：如何用 yaml + ts 架构处理"平台协议犯病"（平台差异、协议 bug、不兼容）。
> 案例来源：tokenrhythm-copilot 插件（luotianyiismywife）对 TokenRhythm 平台的适配经验，
> 该平台 Anthropic / Responses 端点对部分模型有兼容性问题。

---

## 1. 问题：平台"犯病"是常态

中转站上游平台的 Anthropic / Responses 等协议端点往往不标准、不稳定：

| 平台怪癖（TokenRhythm 实测） | 表现 |
|---|---|
| Anthropic 协议非全量 | 部分模型 `supports_anthropic=false`，不支持该协议 |
| Anthropic 参数组合冲突 | DeepSeek 强制思考 + temperature/top_p → 400"请求参数组合无效" |
| Responses 工具格式差异 | OpenAI 嵌套 `function` 格式被拒，需扁平 `{type,name,description,parameters}` |
| Responses 拒绝 tool_call 内容块 | 需文本化回填 `[tool_call]` / `[tool_result]` |
| Responses 流式事件各模型不一致 | 同端点不同模型事件类型不同，不稳定 |
| Anthropic 必带头/必传参数 | `anthropic-version: 2023-06-01` + 必须 `max_tokens` |

**结论**：协议兼容不是"写一次就完"，而是每个平台、甚至每个模型的持续适配。

## 2. 处理模式（tokenrhythm-copilot 已验证）

| 模式 | 做法 |
|---|---|
| **动态能力探测** | 启动时从 `/v1/models` 读 `supports_responses`/`supports_anthropic`，不硬编码模型 ID |
| **默认降级** | `enableResponsesApi`/`enableAnthropicApi` 默认 false → 回退最成熟的 OpenAI 格式 |
| **参数组合修正** | thinking 强制开启时跳过 temperature/top_p（匹配协议规则） |
| **格式转换** | Responses 用扁平工具格式；tool_call 文本化回填 |
| **协议优先级** | auto 模式：Responses > Anthropic > OpenAI（但前两者默认关） |
| **Key 轮换** | 401/402/429/503 轮换 key（错误码可配置） |

## 2.5 双层转换架构（既定 2026-08-22）

> 用户确认：**协议转换归内核、怪癖归插件**。
> 内核把标准格式丢给插件 → 插件改成上游格式 → 上游返回 → 插件转回标准 → 内核回给用户。
> **都是标准格式就不修改，直接转发**。

### 2.5.1 数据流

```
客户端 (OpenAI/Anthropic/Responses/Gemini 格式)
    │
    ▼
内核：入口转换（客户端格式 → 标准 OpenAI）★ 内置四协议解析
    │
    ▼
内核管道：路由 / 计费 / 日志（标准格式下处理）
    │  选上游 → 选协议
    ▼
插件 convert_request：标准 → 上游格式 ★ 平台怪癖修正
    │  （上游支持标准 → 零转换直接转发）
    ▼
上游
    │
    ▼
插件 convert_response：上游格式 → 标准 ★ 平台怪癖修正
    │
    ▼
内核：出口（标准格式回给客户端）
    │
    ▼
客户端
```

### 2.5.2 两层转换的分工

| 转换层 | 谁做 | 位置 | 例子 |
|---|---|---|---|
| **入口**：客户端格式 → 标准 OpenAI | **内核**（内置） | 请求进入 | Anthropic 请求 → 标准 messages |
| **出口**：标准 → 上游格式 | **插件**（convert_request） | 转发前 | 标准 → 上游 anthropic/私有格式 |
| **回程**：上游格式 → 标准 | **插件**（convert_response） | 响应回 | 上游响应 → 标准响应 |
| **标准直通**：上游支持标准 | **零转换** | 无 | one-api / openai 官方 |

### 2.5.3 为什么这样分（避免"全权丢给插件"）

| 方案 | 问题 |
|---|---|
| 协议转换全放内核（四协议内置 + 出口也内置） | 上游私有格式无法覆盖 |
| **全权丢给插件**（用户曾考虑） | ① 通用转换（openai→anthropic）每个插件重复写 ② TS 写重协议逻辑痛苦（tokenrhythm 的 anthropicApi 535 行/responsesApi 600 行） |
| ✅ **内核入口转换 + 插件出口转换** | 入口是通用能力（Rust 写一次）；出口是平台差异（轻量 TS） |

**核心**：
- **入口转换是"通用横切能力"** → 内核 Rust（四协议解析，写一次所有插件受益）
- **出口转换是"平台差异"** → 插件 TS（通常轻量：删参数/扁平化/改模型名）
- **重型的流式协议处理在入口**（内核 Rust 高效），**轻量的格式修正到出口**（插件 TS 灵活）

### 2.5.4 标准直通

上游就是 OpenAI 兼容（one-api / opencode-go / 官方）→ `convert_request`/`convert_response` **透传或省略**：
```
标准 → 标准：不调用转换钩子，直接转发（0 开销）
```
这正是 one-api 示例插件 convert.ts 里"默认透传"的原因。

## 3. 映射到 RelayHub 的 yaml + ts 架构

**平台怪癖 = "yaml 组装不了的部分"，正是 ts 脚本的职责**：

```
yaml（静态规则）                       ts（平台差异实现）
─────────────────                     ─────────────────
protocols: [openai, anthropic, ...]   convert_request()  ← 参数组合修正（thinking+temperature）
preferred: openai                     convert_response() ← 扁平工具格式/文本化回填
fallback: openai                      list_models()      ← 返回 supports_anthropic 等能力标记
```

### 3.1 能力探测 → ts `list_models`

```ts
export async function list_models(ctx: Ctx) {
  const models = await ctx.http.get("/v1/models")
  return models.map(m => ({
    id: m.id,
    capabilities: {                // 能力标记（协议支持情况）
      openai: true,
      anthropic: m.supports_anthropic ?? false,
      responses: m.supports_responses ?? false,
    }
  }))
}
```

### 3.2 协议选择策略 → yaml 声明

```yaml
# upstream.yaml
protocols:               # 支持的协议及优先级
  preferred: openai      # 默认最成熟协议（对应 enableXxxApi 默认 false 的思想）
  order:                 # auto 模式的优先级
    - openai
    - anthropic          # 能力标记支持才启用
    - responses
  fallback: openai       # 协议报错时降级目标
  fallback_on_error:     # 触发降级的错误（状态码 + 错误文本模式）
    - 400                # 参数组合无效（thinking+temperature）
    - 422
    - invalid_parameter  # 错误文本模式（不区分大小写）
```

### 3.3 参数组合修正 → ts `convert_request`

```ts
export async function convert_request(req: Req, ctx: Ctx): Promise<Req> {
  if (req.protocol === "anthropic") {
    // TokenRhythm 实测：thinking 强制开启时带 temperature → 400
    if (req.thinking?.type === "enabled") {
      delete req.temperature
      delete req.top_p
    }
    // Anthropic 必带头
    req.headers["anthropic-version"] = "2023-06-01"
  }
  return req
}
```

### 3.4 协议轮换（新设计，借鉴 key 轮换）

```
请求 → 首选协议（anthropic）→ 400/兼容性错误 → 降级 openai 重试 → 成功
```

```yaml
protocols:
  preferred: anthropic           # 首选协议
  order: [anthropic, openai]     # 降级顺序
  fallback: openai               # 降级目标
  fallback_on_error:             # 触发降级的错误（状态码 + 文本模式）
    - 400                        # 参数组合无效
    - 422
    - invalid_parameter          # 错误文本模式
```

- 与"灰度自动回退"同一心智：**默认保守，异常自动切到更稳的路径**
- 协议轮换 + key 轮换可叠加（先切协议，再切 key）
- ⚠️ 触发降级的错误由 `fallback_on_error` 声明（协议级判定），key 轮换的错误由 `http.yaml` 声明（凭据级判定），两者独立

### 3.5 典型案例：基云律动（tokenrhythm）上游定义

> 用户 2026-08-21 确认："基云律动的话就是 Anthropic/Responses 用 ts，openai 用 yaml"。

**判断逻辑**：不是按"平台"分，而是按"协议在该平台是否标准"分。

| 基云律动的协议 | 表现 | 实现方式 |
|---|---|---|
| **OpenAI 兼容** (`/v1/chat/completions`) | 标准、成熟、无怪癖 | ✅ **yaml 直接组装** |
| **Anthropic** (`/v1/messages`) | thinking+temperature 400、部分模型不支持 | 🔧 **ts**（参数修正 + 能力探测） |
| **Responses** (`/v1/responses`) | 扁平工具格式、tool_call 拒绝、流式不稳定 | 🔧 **ts**（格式转换 + 降级） |

**完整上游定义示例**（与真实 tokenrhythm 插件一致）：

```yaml
# tokenrhythm-1.0.0/upstream.yaml（目录式，Cargo/SemVer 版本）
apiVersion: relayhub.io/v1
kind: Upstream-api-balance
metadata:
  name: tokenrhythm
  version: 1.0.0
depends:
  kernel: "^0.1"

# OpenAI 协议：yaml 直接组装（标准、成熟）
apis:                          # key = 协议名（内核按协议分发）
  openai:
    path: /v1/chat/completions
    method: POST
  anthropic:                   # Claude 系（有怪癖 → ts 修正）
    path: /v1/messages
    method: POST
  responses:                   # OpenAI 新接口（有怪癖 → ts 修正）
    path: /v1/responses
    method: POST
  models:
    path: /v1/models
    method: GET
auth:
  type: bearer
  key_field: Authorization

# 特殊协议：调 ts（平台怪癖在这；新格式：钩子名 → 文件路径）
scripts:
  convert_request:  ./convert.ts   # anthropic/responses 参数修正
  convert_response: ./convert.ts   # 扁平工具/文本化回填 + usage 归一化
  list_models:      ./models.ts    # capabilities 能力探测
  quota_balance:    ./quota.ts     # 余额查询
protocols:
  preferred: openai       # 默认走 openai（最稳）
  order: [openai, anthropic, responses]
  fallback: openai        # anthropic/responses 报错 → 降级 openai
```

**推论**：同样的 OpenAI 端点，不同平台可能也不同（有的平台 OpenAI 端点也有怪癖）——
判断标准始终是：**这个平台的这个协议，是否 yaml 组装得了？组装不了就 ts**。
基云律动恰好是"openai 正常、其他两个犯病"的典型，所以形成"openai 用 yaml，其他用 ts"的格局。

## 4. 对内核的要求

1. `list_models` 返回的能力标记参与路由：协议选择前先查 capabilities
2. 支持协议级 fallback 链（yaml 声明顺序 + 触发错误）
3. `convert_request`/`convert_response` 是平台怪癖的主要落点（参数修正、格式转换）
4. 错误分类：能触发降级的错误（400 参数类） vs 不能的（401 鉴权 → 应走 key 轮换）

## 5. 经验总结

> **"OpenAI 兼容"不是标准，是底线**。平台自称支持 Anthropic/Responses ≠ 真正兼容。
> 处理铁律：
> 1. 默认走最成熟协议（OpenAI 兼容）
> 2. 能力动态探测，不硬编码
> 3. 参数/格式差异在 ts 脚本修正（convert_request / convert_response）
> 4. 报错自动降级（协议轮换 + key 轮换）
