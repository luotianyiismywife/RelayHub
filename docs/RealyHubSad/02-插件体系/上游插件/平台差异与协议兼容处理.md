# 平台差异与协议兼容处理

> 设计记录：如何用 yaml + ts 架构处理"平台协议犯病"（平台差异、协议 bug、不兼容）。
> 案例来源：tokenrhythm-copilot 插件（luotianyiismywife）对 TokenRhythm 平台的适配经验，
> 该平台 Anthropic / Responses 端点对部分模型有兼容性问题。

---

## 1. 问题：平台"犯病"是常态

中转站上游平台的 Anthropic / Responses 等协议端点往往不标准、不稳定：

| 平台怪癖（TokenRhythm 实测） | 表现 |
|---|---|
| Anthropic 协议非全量 | 部分模型 `supports_anthropic=false`，不支持该协议 |
| Anthropic 参数组合冲突 | DeepSeek 强制思考 + temperature/top_p → 400"请求参数组合无效" |
| Responses 工具格式差异 | OpenAI 嵌套 `function` 格式被拒，需扁平 `{type,name,description,parameters}` |
| Responses 拒绝 tool_call 内容块 | 需文本化回填 `[tool_call]` / `[tool_result]` |
| Responses 流式事件各模型不一致 | 同端点不同模型事件类型不同，不稳定 |
| Anthropic 必带头/必传参数 | `anthropic-version: 2023-06-01` + 必须 `max_tokens` |

**结论**：协议兼容不是"写一次就完"，而是每个平台、甚至每个模型的持续适配。

## 2. 处理模式（tokenrhythm-copilot 已验证，2026-08-24 简化）

| 模式 | 做法 |
|---|---|
| **动态能力探测** | 启动时从 `/v1/models` 读 `supports_anthropic`/`supports_responses`，不硬编码模型 ID |
| **格式匹配+报错** | 客户端格式不在 capabilities 里 → 直接 400 报错（不做格式转换） |
| **参数组合修正** | thinking 强制开启时跳过 temperature/top_p（匹配协议规则） |
| **参数格式修正** | Responses 用扁平工具格式；tool_call 文本化回填（同格式内参数修正，非格式转换） |
| **Key 轮换** | 401/402/429/503 轮换 key（错误码可配置） |

## 2.5 格式匹配架构（2026-08-24 简化：不做格式转换）

> **架构简化决策（2026-08-24）**：**内核不做协议格式转换**。
> 客户端用什么格式请求，就按该格式匹配上游；格式不匹配直接 400 报错。
> 用户需要跨格式调用时，自行加本地转换插件或用 ccswitch 等工具。
> 这与 OpenRouter / one-api / new-api 的做法一致——砍掉网关最复杂的部分（协议互转）。

### 2.5.1 数据流

```
客户端 (OpenAI/Anthropic/Responses/Gemini 格式)
    │
    ▼
内核：协议解析（识别客户端格式）★ 不转换，只识别
    │
    ▼
内核管道：路由 / 计费 / 日志
    │  选上游 → 查 capabilities → 格式匹配？
    │    ├─ 匹配 → 直接转发（客户端格式 = 上游格式）
    │    └─ 不匹配 → 400 报错（不做转换）
    ▼
插件 convert_request：参数修正（同格式内，平台怪癖）★ 不做格式转换
    │  （如 thinking+temperature 冲突、必传字段补全）
    ▼
上游（客户端格式 = 上游格式，零转换）
    │
    ▼
插件 convert_response：响应修正 + usage 归一化 ★ 不做格式转换
    │
    ▼
内核：响应回给客户端（同格式，零转换）
    │
    ▼
客户端
```

### 2.5.2 convert_request/response 的职责（简化后）

| 职责 | 谁做 | 例子 |
|---|---|---|
| **格式匹配判定** | **内核** | 客户端 anthropic 格式 → 查 `capabilities.anthropic` → true/false |
| **参数修正** | **插件**（convert_request） | thinking+temperature 冲突删参数、必传字段补全 |
| **响应修正** | **插件**（convert_response） | usage 归一化（extract_usage） |
| **格式转换** | ❌ **不做** | openai↔anthropic 互转不做，不匹配直接报错 |

> ⚠️ **convert_request 不再做格式转换**（2026-08-24 简化）：
> 之前设计"标准→上游格式"的出口转换已废弃。现在 convert_request 只做**同格式内的参数修正**。

### 2.5.3 为什么不做格式转换（2026-08-24 简化决策）

| 方案 | 问题 |
|---|---|
| ~~内核入口转换 + 插件出口转换~~（原设计） | ① 16 种协议组合（4×4）复杂度爆炸 ② 工具调用跨协议（function_call↔tool_use）极复杂 ③ 流式事件跨协议（chunk↔event stream）极复杂 ④ 多模态跨协议 |
| ✅ **不做格式转换，不匹配直接报错** | 零转换 = 零 bug = 行为可预测。大多数上游支持 openai 格式，客户端一般固定一种格式，不匹配是少数场景 |

**核心**：
- **格式匹配是内核职责**（查 capabilities，匹配/报错）
- **参数修正是插件职责**（convert_request，同格式内删参数/补字段）
- **不做格式互转**（openai↔anthropic 等互转不做，用户自行解决）

> 用户 2026-08-24 确认："格式不匹配是用户的事情，可以自己加插件本地转换或者用 ccswitch 之类的"。

## 3. 映射到 RelayHub 的 yaml + ts 架构

**平台怪癖 = "yaml 组装不了的部分"，正是 ts 脚本的职责**：

```
yaml（静态规则）                       ts（平台差异实现）
─────────────────                     ─────────────────
protocols:                            convert_request()  ← 同格式内参数修正（thinking+temperature）
  preferred: openai                   convert_response() ← 扁平工具格式/文本化回填 + usage 归一化
                                      list_models()      ← 返回 capabilities 能力标记
⚠️ 不做格式转换（2026-08-24 简化）
```

### 3.1 能力探测 → ts `list_models`

```ts
export async function list_models(ctx: Ctx) {
  const models = await ctx.http.get("/v1/models")
  return models.map(m => ({
    id: m.id,
    capabilities: {                // 能力标记（协议支持情况）
      openai: true,
      anthropic: m.supports_anthropic ?? false,
      responses: m.supports_responses ?? false,
    }
  }))
}
```

### 3.2 协议选择策略 → yaml 声明（2026-08-24 简化：匹配，不降级）

```yaml
# upstream.yaml
protocols:
  preferred: openai      # 默认协议（客户端未指定格式时用）
  # 注意：不做跨格式降级（2026-08-24 简化）
  # 客户端格式不在 capabilities 里 → 直接 400 报错，不尝试其他格式
  # fallback_on_error 已废弃（跨格式降级不再支持）
```

> ⚠️ **protocols 语义变化**（2026-08-24）：
> - `preferred`：客户端未指定格式时的默认（保留）
> - `order`/`fallback`/`fallback_on_error`：**废弃**（跨格式降级不再支持）
> - 协议报错时只换上游/换 key（同格式内），不换格式

### 3.3 参数组合修正 → ts `convert_request`

```ts
export async function convert_request(req: Req, ctx: Ctx): Promise<Req> {
  if (req.protocol === "anthropic") {
    // TokenRhythm 实测：thinking 强制开启时带 temperature → 400
    if (req.thinking?.type === "enabled") {
      delete req.temperature
      delete req.top_p
    }
    // Anthropic 必带头
    req.headers["anthropic-version"] = "2023-06-01"
  }
  return req
}
```

### 3.4 协议轮换（2026-08-24 废弃：不做跨格式降级）

> **已废弃**：跨格式降级（anthropic 报错→降级 openai）不再支持。
> 原因：不做格式转换 = 不能跨格式降级。
>
> 协议报错时的处理：
> - **参数错误**（400/422）→ passthrough 返回客户端（换格式没用，问题在参数）
> - **上游错误**（5xx/429）→ 同格式内换上游/换 key 重试（Kernel-retry）

### 3.5 典型案例：基云律动（tokenrhythm）上游定义

> 用户 2026-08-21 确认："基云律动的话就是 Anthropic/Responses 用 ts，openai 用 yaml"。

**判断逻辑**：不是按"平台"分，而是按"协议在该平台是否标准"分。

| 基云律动的协议 | 表现 | 实现方式 |
|---|---|---|
| **OpenAI 兼容** (`/v1/chat/completions`) | 标准、成熟、无怪癖 | ✅ **yaml 直接组装** |
| **Anthropic** (`/v1/messages`) | thinking+temperature 400、部分模型不支持 | 🔧 **ts**（参数修正 + 能力探测） |
| **Responses** (`/v1/responses`) | 扁平工具格式、tool_call 拒绝、流式不稳定 | 🔧 **ts**（参数修正，不做格式转换） |

**完整上游定义示例**（与真实 tokenrhythm 插件一致）：

```yaml
# tokenrhythm-1.0.0/upstream.yaml（目录式，Cargo/SemVer 版本）
apiVersion: relayhub.io/v1
kind: Upstream-text-api-balance
metadata:
  name: tokenrhythm
  version: 1.0.0
depends:
  kernel: "^0.1"

# OpenAI 协议：yaml 直接组装（标准、成熟）
apis:                          # key = 协议名（内核按协议分发）
  openai:
    path: /v1/chat/completions
    method: POST
  anthropic:                   # Claude 系（有怪癖 → ts 修正）
    path: /v1/messages
    method: POST
  responses:                   # OpenAI 新接口（有怪癖 → ts 修正）
    path: /v1/responses
    method: POST
  models:
    path: /v1/models
    method: GET
auth:
  type: bearer
  key_field: Authorization

# 特殊协议：调 ts（平台怪癖在这；新格式：钩子名 → 文件路径）
scripts:
  convert_request:  ./convert.ts   # anthropic/responses 参数修正（不做格式转换）
  convert_response: ./convert.ts   # 扁平工具/文本化回填 + usage 归一化
  list_models:      ./models.ts    # capabilities 能力探测
  quota_balance:    ./quota.ts     # 余额查询
protocols:
  preferred: openai       # 默认走 openai（最稳）
  # 不做跨格式降级（2026-08-24 简化）：格式不匹配直接报错
```

**推论**：同样的 OpenAI 端点，不同平台可能也不同（有的平台 OpenAI 端点也有怪癖）——
判断标准始终是：**这个平台的这个协议，是否 yaml 组装得了？组装不了就 ts**。
基云律动恰好是"openai 正常、其他两个犯病"的典型，所以形成"openai 用 yaml，其他用 ts"的格局。

## 4. 对内核的要求

1. `list_models` 返回的能力标记参与路由：格式匹配前先查 capabilities（不支持直接 400 报错）
2. `convert_request`/`convert_response` 是平台怪癖的主要落点（同格式内参数修正，不做格式转换）
4. 错误分类：参数错误（400/422 → passthrough）vs 鉴权错误（401 → key 轮换）vs 上游错误（5xx/429 → retry/cooldown）

## 5. 经验总结

> **"OpenAI 兼容"不是标准，是底线**。平台自称支持 Anthropic/Responses ≠ 真正兼容。
> 处理铁律：
> 1. 默认走最成熟协议（OpenAI 兼容）
> 2. 能力动态探测，不硬编码
> 3. 参数/格式差异在 ts 脚本修正（convert_request / convert_response）
> 4. 报错后换上游/换 key（同格式内，不跨格式降级）
