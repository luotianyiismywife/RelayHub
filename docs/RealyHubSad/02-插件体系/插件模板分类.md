# 上游插件模板分类：Upstream-api vs Upstream-sub

> 设计决策：RelayHub **上游插件**模板按**凭据类型**分两类，不按平台分。
> 用户 2026-08-21 确认：一类是 API Key，一类是 sub2api（账号池）。
> 用户 2026-08-21 进一步确认：**kind 分两种** —— `Upstream-api`（API Key 类）/ `Upstream-sub`（sub2api 账号池类）。
> 参考：[上游插件参考样板-tokenrhythm](./上游插件/上游插件参考样板-tokenrhythm.md)（Upstream-api 完整示例）。
> 上游插件是 RelayHub 三类插件之一（内核插件 / 页面插件 / 上游插件），总览见 [插件体系总览.md](./插件体系总览.md)。

---

## 0. 层级 kind（既定 2026-08-21）

> 用户确认：kind 用 `-` 分隔分层，内核按层级解析。比内部字段更适合内核处理。

### 0.1 kind 树（统一三类插件）

```
Kernel-<能力>              # 内核插件：Kernel-auth / Kernel-ratelimit / Kernel-logging
Page-<能力>                # 页面插件：Page-status / Page-panel
Upstream-<凭据>-<计费>      # 上游插件（凭据 × 计费两维）
  ├── Upstream-api-balance     # key + 余额计费（tokenrhythm / openai 官方）
  ├── Upstream-api-quota       # key + 套餐限额（5小时/周/月，opencodego 模式）
  ├── Upstream-api-free        # key/匿名 + 免费模型（无余额/套餐，IP 维度限速，opencode-zen 模式）
  ├── Upstream-sub-balance     # 账号池 + 余额（少见但可能）
  └── Upstream-sub-quota       # 账号池 + 套餐限额
```

> `Upstream-api-free`（2026-08-24 新增）：免费模型场景（如 opencode zen），无余额/套餐查询钩子，
> 配额在 **IP 维度**（服务端按 IP 限速），限速判定/绕行归内核（network.proxy_pool 换出口 IP）。
> 示例：`Example/UpStream/Api/opencode-zen/`

### 0.2 内核解析规则（`-` 分隔，前缀匹配，层级 dispatch）

```
kind = "Upstream-api-quota"
  ├─ 第 1 层 "Upstream"  → 上游插件（加载上游 schema 组）
  ├─ 第 2 层 "api"       → API Key 类（校验: 无 pool/refresh/validate 字段）
  └─ 第 3 层 "quota"     → 套餐计费（校验: quota_usage 必配，无 quota_balance）
```

- 每层只有**有限枚举**，schema 校验按层级逐步收紧
- 内核**加载前就知道类型** → 直接选校验器 + 实例化路径（无需读内部字段分支）
- **未来加维度不炸**：如账号池再分 cookie/oauth → `Upstream-sub-cookie-quota`

### 0.3 为什么层级 kind 比"内部字段"更适合内核

| | 内部字段（`billing: balance\|quota`） | 层级 kind（`-` 分隔） |
|---|---|---|
| 内核加载 | 先加载再读字段才知道类型 | **加载前就知道类型**，直接 dispatch |
| schema 校验 | 校验器内部 if 分支 | 按层选择校验器，逐层收紧 |
| 实例化路径 | 运行时再分支 | 编译期/加载期确定 |
| 未来扩展 | 加字段 = 改内核逻辑 | 加一层 = 新枚举，不动旧逻辑 |
| 可读性 | 看字段才知道 | **看 kind 一眼识别** |

### 0.4 与 K8s 对照

| K8s | RelayHub |
|---|---|
| `apiVersion: apps/v1` + `kind: Deployment` | 层级编码在 kind（`-` 分隔） |
| API server 按 GVK 路由 schema/handler | 内核按 kind 层级选校验器/实例化器 |
| 每种 kind 独立 schema | 每层独立校验规则，逐层收紧 |

> K8s 用 apiVersion 管版本、kind 管类型；RelayHub 用**一个 kind 字段 `-` 分层**管类型，
> 版本仍由文件名（`-1.0.0`）管 —— 类型/版本两维解耦不变。

### 0.5 上游插件计费维度（Upstream-api 内部）

> **计费情况对号入座表**（插件作者照着填，模板注释已同步指向这里）：
>
> | 平台情况 | 写在哪 | 说明 |
> |---|---|---|
> | 只有总余额 | `quota_balance` 返回 `{ total }` | 最简 |
> | 充值+限时赠送分开 | `quota_balance` 返回 `total/permanent/limited` | 每笔限时赠送达到期时间 |
> | 余额有有效期 | `rotation.balance_ttl` | 过期内核重新查询 |
> | 查余额要 cookie | `auth.query.cookie` | 转发 key 查不了余额 |
> | 峰时消耗翻倍 | `billing.peak`（或钩子透传） | PeakRate：start/end/multiplier/timezone |
> | 单窗口限额 | `quota_usage` 返回 1 个 window | 最简 |
> | 多窗口（5h/周/月） | `quota_usage` 返回多个 window | kind 滚动/日历 |
> | 日限额/3天限额 | window.period = `daily`/`3d` | kind 对应 calendar/rolling |
> | 套餐到期时间 | `planExpiresAt` | 整个套餐何时结束 |
> | 额度耗尽回退余额 | `fallbackToBalance` | 套餐→余额兜底 |
> | 各窗口独立重置时间 | `windows[].resetsAt`（必填） | 内核判断过期/调度刷新 |
> | 平台返回 usage 明细（缓存/推理） | `convert_response` 的 `extract_usage` | 透传 TokenUsage 给 Kernel-billing |
>
> ⚠️ **成本计算（多维费率/阶梯/换算/预扣）不在上游插件**，全归内核/内核插件（见 §0.6 与待办 J 组）。

| 计费模式 | 凭据 | 用量形态 | hooks | 代表 |
|---|---|---|---|---|
| **balance** | key + 余额 | 总余额 = 充值 + 限时赠送（分开展示） | `quota_balance` 必配 | tokenrhythm / openai 官方 |
| **quota** | key + 套餐 | 套餐到期 + 多窗口用量（5小时/周/月） | `quota_usage` 必配（含 planExpiresAt/windows） | opencodego、订阅制平台 |
| **free** | key/匿名（如 "public"） | 无余额/套餐；配额在 **IP 维度**（服务端按 IP 限速） | **无计费钩子**（quota_balance/quota_usage 都不配）；限速判定/绕行归内核 | opencode-zen |

**Balance 结构（balance 类，2026-08-22 细化）**：
```ts
interface Balance {
  total: number              // 总余额 = permanent + limited 合计
  currency?: string          // 货币（可选，金额统一为数字）
  permanent?: number         // 充值余额（不过期）
  limited?: {                // 限时赠送余额（每笔分开，tokenrhythm 实测平台行为）
    amount: number           // 金额
    expiresAt: string        // 到期时间（ISO8601）
  }[]
  peak?: PeakRate            // 峰谷定价：峰时余额扣减倍率（可选，见下）
}
```

**Usage 结构（quota 类，2026-08-22 细化）**：
```ts
interface Usage {
  planExpiresAt?: string     // 套餐到期时间（整个套餐何时结束）
  windows: {                 // 各时间段额度用量（多窗口）
    period: string           // "5h" | "3d" | "daily" | "weekly" | "monthly"
    kind: "rolling" | "calendar"  // ★ 窗口类型（2026-08-22 新增）
                             //   rolling  ：滚动窗口（5h/3d：过去 N 时长滑动）
                             //   calendar ：日历固定边界（daily/weekly/monthly）
    used: number             // 已用额度
    limit: number            // 总额度
    percent?: number         // 已用百分比（可算，平台给了才填）
    windowStart?: string     // ★ 窗口开始时间（calendar 类，sub2api 模式：
                             //   daily_window_start 等；rolling 可省）
    resetsAt: string         // ★ 必填：窗口下一次重置时间（ISO8601）
                             // ★ 每个窗口都必须有；内核依赖它判断窗口过期/调度刷新
                             // ★ calendar：下一个日历边界；rolling：now+周期时长
                             // ★ 平台不直接给时由插件兜底推断（模板 resolveResetsAt）
    peak?: PeakRate          // ★ 峰谷定价：此窗口峰时消耗倍率（可选，每窗口可不同）
  }[]
  fallbackToBalance?: boolean  // 额度耗尽后是否回退余额
  peak?: PeakRate            // 全局峰谷定价（可选，作用于所有窗口）
}
```

**峰谷定价（PeakRate，2026-08-22 调研 sub2api 实现）**：
```ts
interface PeakRate {
  start: string       // 峰时开始（24h 格式 "14:00"，服务器时区）
  end: string         // 峰时结束（"18:00"）
  multiplier: number  // 峰时消耗倍率（2 = 峰时消耗翻倍）
  timezone?: string   // 时区（IANA "Asia/Shanghai"；缺省 = 服务器时区）
}
```

> **窗口类型对照表**（kind × period）：
>
> | period | kind | 重置语义 | 参考 |
> |---|---|---|---|
> | `5h` | rolling | 查询时刻 + 5h（旧额度滑出） | opencode-go |
> | `3d` | rolling | 查询时刻 + 3d | 未来平台（3天限额） |
> | `daily` | calendar | 每天 00:00（服务器时区） | sub2api（ChatGPT Plus/Pro） |
> | `weekly` | calendar | 每周一 00:00 | opencode-go / sub2api |
> | `monthly` | calendar | 每月 1 日 00:00 | opencode-go / sub2api |

### 0.6 Token 多维用量（内核成本计算的输入，2026-08-22 全网调研新增）⭐

> **上游插件的 Usage 结构是"套餐余量"（窗口），不是"单次请求消耗"**。
> 单次请求的消耗由**响应 usage** 提供（标准 OpenAI 格式），但真正的成本是**多维**的。
> 这一节是 `Kernel-billing` 的输入契约（J1/J2/J3，见待办 J 组）。

**成本 = Σ(各维 token/单位 × 各维单价)**，维度参考（new-api `TokenParams` 10 维 / OpenRouter 15 维）：

```ts
interface TokenUsage {           // 单次请求的用量（从上游响应 usage 解析）
  prompt: number                 // 输入文本 token
  completion: number             // 输出文本 token（不含单独计价的子类）
  // —— 子维度（平台返回才填；缺省按 0 处理，且从 prompt/completion 中扣除）——
  cacheRead?: number             // 缓存命中读 token（便宜，约 1/10 价）
  cacheWrite?: number            // 缓存写入创建 token（贵，约 1.25x；Claude 5min TTL）
  cacheWrite1h?: number          // 缓存写入 1h TTL（Claude 特有）
  reasoning?: number             // 推理 token（单独费率或更高费率）
  imageIn?: number               // 图片输入 token（视觉）
  imageOut?: number              // 图片输出 token（生图，可能按张）
  audioIn?: number               // 音频输入 token
  audioOut?: number              // 音频输出 token
  toolCalls?: number             // 工具调用 token（可选）
}

interface PriceTable {           // 模型价格表（J7，Kernel-billing 消费）
  [model: string]: {
    input?: number               // 输入单价（$/1M token 或 quota 单位）
    output?: number              // 输出单价
    cacheRead?: number           // 缓存读单价
    cacheWrite?: number          // 缓存写单价（5min TTL）
    cacheWrite1h?: number        // 缓存写单价（1h TTL）
    reasoning?: number           // 推理单价
    image?: number               // 图片单价（输入/输出）
    audioPerSecond?: number      // 音频实时按秒（realtime 模型）
    imagePerOutput?: number      // 生图按张（image generation）
    tier?: {                     // 阶梯定价（J3）：输入超过 threshold 换费率
      minPromptTokens: number
      input: number
      output: number
    }[]
    perRequest?: number          // 按请求计费（web search 等）
  }
}
```

**关键规则**（2026-08-22 调研结论）：
1. **子维度从主维度扣除**：返回了 cacheRead 时，prompt 应剔除缓存部分（不重复计费）—— new-api 语义
2. **缺失值 ≠ 0**：unknown 与 explicit 0 必须区分，不能把"未知费率"伪装成"免费"（J9）
3. **阶梯分段计价**：请求跨档 → 分段算（低于阈值按 A 价、超出按 B 价）（J3）
4. **时间窗/条件倍率**：PeakRate 是特例，泛化为条件规则（J4）
5. **流式预扣结算**：先按 prompt 估算预扣，完成后按实际 usage 回填 diff（J5，one-api 模式）
6. **特殊单位**：realtime 按秒、生图按张、web search 按请求（J6）

> ⚠️ 上游插件**不做**以上计算：只透传平台返回的 usage 明细（`input_token_details` 等原始对象）和余量（Balance/Usage）。
> 全部成本计算在 `Kernel-billing`（价格表 J7 + 维度 J1-J4 + 换算 J12）。

## 1. 为什么按凭据类型分

| | Upstream-api | Upstream-sub |
|---|---|---|
| **凭据** | 单个 API Key（永不过期） | 一组账号（OAuth 文件/Cookie，会过期） |
| **核心复杂度** | 协议转换（convert_request/response） | **凭据生命周期**（刷新/验证/轮换/余量） |
| **refresh_credentials** | ❌ 不需要 | ✅ **核心钩子** |
| **账号选择** | 无（一个 key） | **账号池轮换**（健康度/余量/最少使用） |
| **余额/用量** | 可选 | **必配**（cookie 查询、余量管理） |
| **凭据字段** | 单字段 `key` | 多字段（access_token/refresh_token/UA/account_id...） |
| **validate_credential** | 可选（查 key 有效性） | **必配**（账号用前验证） |

**判断标准**：凭据是"一个 key"还是"一组会过期的账号"。

## 2. 模板一：Upstream-api（tokenrhythm / openai / anthropic 官方）

### 2.1 yaml 骨架

> ⚠️ **kind 是三级**：`Upstream-api-balance`（余额计费）或 `Upstream-api-quota`（套餐限额）—— 不是 2 级 `Upstream-api`！
> 两种只差计费方式（quota_balance vs quota_usage + billing 段），其余结构相同。
> 完整可运行的模板见 `Plugin/Template/UpStream/Api/example-plugin/`。

```yaml
# <name>-1.0.0/upstream.yaml
apiVersion: relayhub.io/v1
kind: Upstream-api-balance      # ← API Key 类：balance（余额计费）或 quota（套餐限额），二选一
metadata:
  name: <platform>              # ← 与目录名一致
  version: 1.0.0                # ← Cargo/SemVer 三级，与目录名一致

# 依赖声明（Cargo 规则，见插件开发规范 §1.5）
depends:
  kernel: "^0.1"

apis:                          # key = 协议名，内核按协议分发
  # 平台支持哪些协议就写哪些（不需要的删掉），四协议内核内置：
  openai:            { path: /v1/chat/completions, method: POST }   # OpenAI 协议（兼容一切）
  anthropic:         { path: /v1/messages, method: POST }           # Claude 系
  responses:         { path: /v1/responses, method: POST }          # OpenAI 新接口
  gemini:            { path: /v1beta/models/*:generateContent, method: POST }  # Google 系
  # 模型列表端点：可以留着做"原始数据源"，但最终模型列表统一由 list_models 钩子（models.ts）
  # 归一化返回 —— 内核不用这个端点，是否声明仅影响钩子内部 ctx.http 可访问性
  models:            { path: /v1/models, method: GET }
auth:
  type: bearer                     # 或 header/query
  key_field: Authorization
  credentials: ref:<name>-prod     # 单个 key（docker secret）
  # query:                        # 可选：查余额/套餐的附加凭据（cookie/session）
  #   cookie: ref:<name>-session  #   —— 转发 key 查不了余额的平台才需要
special:
  headers:
    <protocol>: { ... }            # 静态强制头（按协议）
protocols:
  preferred: openai               # 默认协议（客户端未指定格式时用）
  # 不做跨格式降级（2026-08-24 简化）：格式不匹配直接报错
rotation:                          # key 轮换错误判定（判定在插件，机制在内核）
  http_rules: ./http.yaml          # 状态码 → 动作（rotate/cooldown/retry/passthrough）
  error_patterns:                  # 错误文本模式（不区分大小写）
    - "insufficient_balance"
  balance_ttl: 5m                  # 余额有效期（可选）
scripts:                           # 钩子 → 文件映射（新格式：钩子名: 文件路径）
  convert_request:  ./convert.ts   # 协议参数修正（如有）
  # convert_response: ./convert.ts # 响应修正 + usage 归一化（extract_usage）
  list_models:      ./models.ts    # 默认必配：模型列表归一化（唯一权威来源）
  quota_balance:    ./quota.ts     # kind=balance 必配（余额查询）
  # quota_usage:    ./quota.ts     # kind=quota 必配（套餐限额查询）
  # ❌ 无 refresh_credentials（key 不过期）
  # ❌ 无 validate_credential（非必须）
```

## 3. 模板二：Upstream-sub（sub2api / CPA / gpt4free 网页源）

### 3.1 yaml 骨架

> ⚠️ **kind 是三级**：`Upstream-sub-balance` 或 `Upstream-sub-quota`（账号池 × 计费方式）—— 不是 2 级 `Upstream-sub`！

```yaml
# <name>-1.0.0/upstream.yaml
apiVersion: relayhub.io/v1
kind: Upstream-sub-balance       # ← 账号池类：balance 或 quota，二选一
metadata:
  name: <platform>              # ← 与目录名一致
  version: 1.0.0                # ← Cargo/SemVer 三级，与目录名一致

# 依赖声明（Cargo 规则，见插件开发规范 §1.5）
depends:
  kernel: "^0.1"

auth:
  type: account-pool               # ← 账号池（一组 oauth-file/cookie 凭据）
  pool:
    select: healthy_least_used     # 选账号策略：healthy / least_used / round_robin
    validate_before_use: true      # 用前验证
    min_healthy: 1                 # 最少健康账号数（低于则告警）
  fields:                          # 账号字段结构（由平台决定）
    - access_token
    - refresh_token
    - user_agent
    - account_id
    - cookie
  refresh:                         # 凭据刷新策略
    every: 10m
    expires_within: 24h
  credentials: ref:<name>-pool     # 账号池引用（docker secret 目录/文件）

apis:                          # key = 协议名（与 Api 类一致）
  openai:            { path: /v1/chat/completions, method: POST }
  models:            { path: /v1/models, method: GET }
protocols:
```

### 3.2 auth.ts / quota.ts 核心钩子

```ts
// 账号池轮换：内核选账号，脚本提供验证/刷新
export async function validate_credential(ctx: Ctx): Promise<{ ok: boolean, reason?: string }> {
  // 用前验证：401 → 标记不可用并从池中摘除
  const res = await ctx.http.get("/v1/models")
  if (res.status === 401) return { ok: false, reason: "unauthorized" }
  return { ok: true }
}

export async function refresh_credentials(ctx: Ctx): Promise<void> {
  // 对快过期的账号批量刷新（sub2api token_refresher 逻辑）
  for (const cred of ctx.pool.getExpiring()) {
    const newTokens = await ctx.http.post("/api/auth/refresh", {
      refresh_token: cred.refresh_token,
      user_agent: cred.user_agent,        // 部分平台刷新要带原 UA
    })
    await ctx.credential.update(cred.id, { access_token: newTokens.access_token })
  }
}

export async function quota_balance(ctx: Ctx): Promise<Balance> {
  // 有些平台只能用 cookie 查余额（无法用 key 查）—— 归一化结构 total/permanent/limited
  const data = await ctx.http.get("/v1/quota", { cookie: ctx.credential.cookie })
  return { total: data.balance }           // ← 新契约字段是 total（旧 balance 已废弃）
}
```

## 4. 模板选择与组合

```
平台凭据是单个 key？      → kind: Upstream-api-balance / Upstream-api-quota（轻）
平台凭据是账号池/会过期？  → kind: Upstream-sub-balance / Upstream-sub-quota（重，凭据生命周期）
同一平台两种都有？        → 两个上游定义，分别套模板（同 name 不同 credential）
```

**kind 校验规则**（内核加载时，三级）：

- `Upstream-api-*`：`refresh` / `pool` / `validate_before_use` 等字段**禁止出现**（schema 拒绝）
- `Upstream-sub-*`：`pool` / `fields` / `refresh` / `min_healthy` 为**必填**；`scripts` 必须含 `refresh_credentials` + `validate_credential`
- 第 3 层计费校验：`-balance` 必配 `quota_balance`（无 `billing` 段）；`-quota` 必配 `quota_usage` + `billing` 段
- 校验器按 kind 分流（不同 schema），加载失败报具体字段错误

## 5. 对内核的要求（账号池新增）

1. **账号池管理**：凭据组（多 UUID）、健康标记、余量记录
2. **选账号策略**：`healthy_least_used` / `round_robin` / `least_balance`（yaml 声明，内核实现）
3. **池化刷新**：`refresh_credentials` 批量刷新快过期账号（区别于单凭据）
4. **validate_before_use**：用前验证，401 摘除账号，min_healthy 告警
5. **cookie 支持**：账号池类常需 cookie 查余额/用量，脚本可读 cookie 字段
