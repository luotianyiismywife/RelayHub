# RelayHub 插件体系总览

> 设计决策：RelayHub 插件分三类 —— **内核插件 / 页面插件 / 上游插件**。
> 用户 2026-08-21 确认。
> 上游插件按模态 × 凭据族分：`Upstream-<模态>-<凭据>-<计费>`（模态：text/image/audio/video/mix；凭据：api/sub；计费：balance/quota/free）。
> 实际 kind 是四级（模态 × 凭据 × 计费），如 `Upstream-text-api-balance` / `Upstream-text-sub-quota`（见插件模板分类 §0）。

---

## 1. 三类插件（既定 2026-08-21）

| 插件类型 | kind（层级 `-` 分隔） | 扩展什么 | 代表例子 |
|---|---|---|---|
| **内核插件** | `Kernel-<能力>` | 内核请求管道能力（中间件/钩子） | `Kernel-auth`、`Kernel-ratelimit`、`Kernel-logging` |
| **页面插件** | `Page-<能力>` | 展示层（CLI 输出 / 未来 web 面板） | `Page-status`、`Page-panel` |
| **上游插件** | `Upstream-<模态>-<凭据>-<计费>` | 上游接入（协议匹配/凭据/能力） | `Upstream-text-api-balance`、`Upstream-text-sub-quota` |

**kind 分层解析**（内核按 `-` 分隔前缀匹配）：

```
kind = "Upstream-text-api-quota"
  ├─ 第 1 层 "Upstream"  → 上游插件
  ├─ 第 2 层 "api"       → API Key 类（无 pool/refresh）
  └─ 第 3 层 "quota"     → 套餐计费（quota_usage 必配）
```

- 每层有限枚举，schema 逐层收紧
- 内核加载前就知道类型 → 直接 dispatch（详见 [插件模板分类](./插件模板分类.md) §0）

**定位关系**：

```
                 ┌─────────────────────────────────┐
                 │         RelayHub 内核             │
                 │  ┌───────────┐  ┌────────────┐   │
                 │  │ 内核插件    │  │ 页面插件     │   │
                 │  │ (管道钩子)  │  │ (展示层)    │   │
                 │  └───────────┘  └────────────┘   │
                 │        请求管道 + 调度              │
                 └──────────────┬──────────────────┘
                                │ 调用
                 ┌──────────────▼──────────────────┐
                 │        上游插件（yaml + ts）       │
                 │  ┌─────────────┐ ┌────────────┐  │
                 │  │Upstream-文本│ │Upstream-账号│ │
                 │  │ (api key 类)│ │ (sub 池类) │  │
                 │  └─────────────┘ └────────────┘  │
                 └──────────────────────────────────┘
```

## 2. 内核插件（KernelPlugin）

扩展**内核请求管道**的能力，挂载在请求生命周期上的钩子。

**可能的能力点（待对齐）**：

| 能力点 | 作用 | 例子 |
|---|---|---|
| `auth` | 入站鉴权（对客户端） | 自定义 key 校验、JWT、多用户 |
| `ratelimit` | 限流 | 按用户/模型/全局 |
| `logging` | 日志/审计 | 请求日志、用量记录 |
| `protocol` | 协议处理器 | SSE 处理、流式改写 |
| `routing` | 路由策略 | 负载均衡、权重、灰度 |
| `billing` | **成本计算（扩展需求）** | 余额折扣系数 → 真实成本 |
| `middleware` | 通用中间件 | CORS、自定义头、重写 |

**成本计算 = Kernel-billing 插件（既定 2026-08-21）**：

> 用户确认：**成本计算是扩展需求，内核只负责转发，不该内置**。
> 场景：1 人民币买了 3 刀余额 → 平台返回"用了 3 刀"，真实成本只有 1 人民币。

```
Upstream 插件: quota_balance → { total: 3 }        # 平台数据（3刀）
                    ↓
Kernel-billing: 乘折扣系数                            # config: { paid: 1, got: 3 }
                    ↓
输出: 真实成本（按用量比例换算，如用了 1 刀 → 成本 0.33 人民币）
```

- **内核只做转发**（微内核哲学），成本计算不是转发的必需品 → 做成可启用/禁用的内核插件
- 折扣配置在 config.yaml：`billing: { tokenrhythm: { paid: 1, got: 3 } }`
- 上游插件**不掺成本**（只返回平台数据），成本计算全在 Kernel-billing
- 未来可组合：`Kernel-billing` + `Page-status`（展示真实成本）

**多维计费（2026-08-22 全网调研，待办 J 组）**：

> 真实成本不是简单的"总 token × 单价"，而是**多维度**的：缓存读/写、推理、图片、音频、阶梯分档、条件倍率、预扣结算。
> 详见 [插件模板分类 §0.6](./插件模板分类.md)（TokenUsage 多维用量 + PriceTable 价格表契约）与 [待办 J 组](../待办.md)。

```
Kernel-billing 职责：
  1. 价格表（J7）：模型多维单价（输入/输出/缓存/推理/图片/音频/秒/张）
  2. 维度计算（J1）：成本 = Σ(各维 token/单位 × 各维单价)
  3. 阶梯分档（J3）：输入超阈值换费率，跨档分段计价
  4. 条件倍率（J4）：峰谷 PeakRate 是特例，泛化为时间窗/头/星期条件
  5. 单位换算（J12）：美元 → 人民币 → quota（new-api 体系）
  6. 缺失值语义（J9）：unknown ≠ 0，不能把未知伪装成免费

内核转发引擎职责：
  预扣/结算（J5）：流式先按 prompt 估算预扣 → 完成后按实际 usage 回填 diff；中断回滚

上游插件职责（不变）：只透传平台数据
  Balance/Usage（套餐余量）+ 响应 usage 明细（TokenUsage，convert_response 归一化）
```

**与上游插件的区别**：
- 内核插件**不接入上游**，它改变**内核自己的行为**（怎么处理请求、怎么选路、怎么计算、怎么记录）
- 上游插件**接入外部平台**，它定义**怎么跟某个平台对话**

**形态**：可能也是 yaml + ts（声明挂载点 + 实现逻辑），也可能是 Rust 内建扩展点（待对齐）。

## 3. 页面插件（PagePlugin）

扩展**展示层**（`relayhub status` 输出、CLI 表格、未来 web 面板）。

**可能的能力点（待对齐）**：

| 能力点 | 作用 |
|---|---|
| `status_section` | 在 `relayhub status` 里加自定义区块 |
| `command` | 注册自定义子命令（`relayhub <name>`） |
| `panel` | 未来 web 面板的页面/组件 |
| `metric` | 自定义指标展示 |

**与上游插件的关系**：上游插件提供**数据**（quota_balance 等），页面插件提供**展示**（怎么呈现）。
两者可配合：上游插件产出统一数据 → 页面插件决定怎么画。

## 3.1 前后端分离：1 个内核插件 ↔ N 个页面插件（既定 2026-08-21）

> 用户确认：**一个内核插件（负责计算）可对应多个页面插件（负责展示），前后端分离**。

```
Kernel-billing（计算真实成本）          Page-status（CLI 状态展示）
        │  产出标准数据                    │
        ├──────────────────►  Page-text（纯文本输出）
        ├──────────────────►  Page-web（未来 web 面板组件）
        └──────────────────►  Page-alert（异常告警展示）
```

**核心机制**：

1. **内核插件产出"标准数据"**（结构化，如真实成本、用量、余额）
2. **多个页面插件消费同一份标准数据**，各自决定怎么展示
3. **前后端分离**：内核插件不关心怎么展示；页面插件不关心数据怎么来的
4. **组合自由**：一个内核插件配 1 个页面插件，或配 N 个，按需安装

**类比**：VS Code 的 Provider（内核插件产数据）可以被多个 UI 表面消费（命令面板/悬停/状态栏）。

**示例组合**：
```
Kernel-billing + Page-status   → relayhub status 显示"真实成本"
Kernel-billing + Page-web      → web 面板显示成本图表
Kernel-billing + Page-alert    → 余额/成本异常时告警
```

## 4. 上游插件（Upstream-<模态>-<凭据>-<计费>）

详见 [插件模板分类](./插件模板分类.md)（完整的两类模板、yaml 骨架、hooks 钩子）。

| kind | 类型 | 凭据 | 核心复杂度 |
|---|---|---|---|
| `Upstream-<模态>-api-<计费>` | key 类 | 单个 key（不过期） | 协议转换 |
| `Upstream-<模态>-sub-<计费>` | 账号池类 | 一组账号（会过期） | 凭据生命周期 |

## 5. 三类插件的交互

```
客户端请求
    │
    ▼
[内核插件：auth 鉴权] → [内核插件：ratelimit 限流]
    │
    ▼
[内核：路由/选上游]  → [上游插件：convert_request → 转发 → convert_response]
    │                              │
    │                              └→ [上游插件：refresh_credentials 定时刷新]
    ▼
[内核插件：logging 记录] ──► 产出标准数据
                              │
                    ┌─────────┼─────────┐
                    ▼         ▼         ▼
              [Page-a 展示] [Page-b 展示] [Page-c 展示]   ← 1 内核插件 → N 页面插件
```
